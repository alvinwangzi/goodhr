# HRPlus 执行计划实现规格

更新日期：2026-10-08

本功能让 HR 提前设置招聘日期、每日工作时间段、岗位顺序和执行动作。本地程序按计划运行，在找简历过程中及时回复候选人，并按每个人的到期时间安排复打招呼。同一天跨时间段继续进度；周期计划次日从第一个岗位开始新一轮。当天未完成只记录日志并发送报告，不关闭或暂停计划。

本文是实现规格，不表示功能已经开发或通过运行验收。下文明确区分用户已确认规则和第一版工程默认值。

## 1 已确认规则和第一版范围

### 1.1 已确认规则

- 计划支持一次性和周期性执行。
- 一天可设置多个时间段，时间段不能重叠。
- 不同计划允许配置相交的执行时间；实际开始前检查并原子取得执行权，已有任务或收尾动作占用时排队后延并记录日志。
- 岗位只排先后顺序，不设置每个岗位的开始和结束时间。
- 同一岗位允许重复添加，每条执行项分别配置动作，按执行项顺序推进。
- 每个岗位可勾选打招呼、自动回复、自动复打招呼，至少选择一个。
- 勾选自动回复时，可选择是否优先回复。
- 自动复打招呼独立计时，在其他动作进行期间也要检查，不能等其他动作整段完成。
- 浏览器动作交替执行，不同时操作同一页面。
- 在执行后续岗位时，继续检查本计划中已经开始执行的岗位的新回复和到期复打。
- 第一版不增加各动作的结束数量配置。打招呼沿用岗位单次上限；回复和复打按待处理数据结束。
- 时间段结束时随机延后 3–6 分钟安全收尾；同一天下个时间段继续未完成进度。
- 最后一个时间段结束仍未完成，只记录日志并发送报告，计划保持启用。
- 周期计划下个执行日从第一个岗位重新开始，单次打招呼计数重新计算。
- 候选人的历史回复记录、复打次数、上次联系时间和去重记录不因新一天清零。
- 一次性计划结束后不自动产生第二天的执行。
- 执行中的计划不允许编辑，必须先停止并完成安全收尾后才能编辑。停止后再次执行，从计划第一执行项开始。
- 支持用户点击“立马开始”，也支持到计划时间自动触发；两种入口共用执行锁和启动校验。
- “立马开始”只在计划允许的日期和时间段内执行；时间段外等待下个匹配时间段自动触发。
- 所有任务完成后结束本次运行，不长期保持消息值守。

### 1.2 第一版工程默认值

以下作为实现默认值，后续可调整，不新增用户配置负担：

- 周期选项为每天、每周指定星期；支持有效起止日期，默认采用 Asia/Shanghai 时区。
- 优先回复默认关闭，用户明确开启后生效。
- 同一本地程序一次只运行一个执行计划或手动岗位任务，复用现有单任务运行限制。
- 第一版不支持跨午夜时间段；当天开始时间必须早于结束时间。
- 同一计划内允许重复岗位，也允许重复动作组合，不按岗位 ID 合并或删除执行项。
- 全部工作提前完成后结束当日运行，不无限等待未来新消息或下一次复打时间。
- 本地程序离线或电脑关机时不能操作页面。当天重新上线可在剩余有效时间内继续；不补跑往日运行。
- 不新增依赖优先；确需安装依赖时先检查国内代理配置。

## 2 前端页面和操作

新增“执行计划”入口，岗位管理保留现有手动开始能力。

### 2.1 计划编辑

| 区域 | 配置内容 | 校验 |
| --- | --- | --- |
| 基础信息 | 计划名称、启用状态 | 名称必填 |
| 执行日期 | 一次性日期，或周期、星期、有效日期范围 | 至少有一个有效执行日期 |
| 每日时间 | 一个或多个开始和结束时间 | 不跨午夜，不重叠 |
| 岗位编排 | 从可访问岗位中添加，向上向下移动或拖动排序；同一岗位可多次添加 | 至少一个执行项，每项分别选择动作 |
| 执行动作 | 打招呼、自动回复、自动复打招呼 | 至少勾选一个，平台必须支持 |
| 回复偏好 | 优先回复开关 | 未勾选自动回复时关闭且不显示 |
| 报告 | 页面报告，复用已有邮件配置 | 无邮箱时明确显示仅页面报告 |

展示岗位现有打招呼上限、复打间隔和次数限制，避免用户误以为执行计划覆盖了岗位或个人配置。不显示第一版未实现的结束数量输入框。

每条执行项有独立编号、岗位和动作配置。例如，“Java 岗位—自动回复”与“Java 岗位—打招呼”是两个执行项，前一项当前工作完成后才进入后一项。

支持以下编排，不强制把一个岗位的所有动作放在一起：

- 先处理消息：Java 自动回复 → Java 自动复打招呼 → Java 找简历打招呼。
- 先统一找简历：Java 打招呼 → 销售打招呼 → Java 自动回复 → 销售自动回复。
- 一个执行项同时选择多个动作：在该项内按优先回复和复打到期规则交替执行。

前端明确提示：消息动作只有在对应执行项开始后才激活；已激活的消息动作可以在后续执行项期间穿插执行。

### 2.2 运行展示

- 计划状态与当日运行状态分别显示，不能因当日未完成把计划显示为已停用。
- 展示正在执行的岗位和动作，以及各岗位打招呼、回复、复打的成功数量。
- 展示下个工作时间段、待回复数量、已到期复打数量；数量不可可靠读取时显示未知，不伪造为零。
- 自动间歇状态显示“等待下个时间段”；正常结束显示“当日完成”；未完成显示“当日未完成，计划仍启用”。
- 提供“立马开始”“按计划时间执行”“停止”“停用”“编辑”和“查看报告”。
- 点击停止后显示“正在收尾”，停止领取新操作，完成已经发送动作的必要确认。本地确认停止后将旧运行结算为“用户停止”，保留日志和发送记录，并开放编辑；不能只因用户点过停止就立即开放保存。
- 执行中、收尾中禁止编辑。等待当天后续时间段的运行仍属于同一进行中的运行，编辑前同样需要停止。
- 用户停止同时关闭自动触发，跨时间段和跨日都不会自行解除。保存编辑也不会自动开始；用户选择“立马开始”或“按计划时间执行”后重新启用。
- 停止后无论是否编辑，再次开始都创建新运行，从第一执行项开始，不接续旧游标和单次计数。候选人历史、已发送记录和待补传结果始终保留。
- 停止后编辑保存生成新版本，新运行采用保存后的配置，不把旧编排中的执行项进度套到新编排上。
- 无当前运行的计划可以编辑；保存配置与决定是否启动分开处理。停用计划停止当前运行及未来自动启动。
- 后端在保存时再次检查停止确认、运行状态与配置版本；编辑和定时启动不能同时成功。设备离线、尚未确认安全停止时，进行中的计划不能编辑。

### 2.3 立马开始和定时触发

- 两种启动方式都校验登录、会员、设备、平台能力、配置版本及执行锁，不因手动启动跳过安全条件。
- 当天因自动间歇而等待时段的运行，保留原进度；到下个时间段继续。用户显式停止已经结束了旧运行，再次开始一律从第一项新建运行。
- 连点“立马开始”、请求超时重试以及同时发生的定时触发，必须返回同一运行，不创建并行或重复运行。
- 按计划时间执行用于重新启用自动触发。当前日期和时间符合配置时可以触发，否则等待下个匹配时间段。
- 手动开始不修改用户配置的周期和时间段，跨日仍按照周期执行。
- 时间段外点击“立马开始”只启用计划并显示“等待下个执行时间”，不操作招聘页面；当前处于随机延后的收尾范围时也不能以此新建一轮，必须在名义时间段内启动。
- 时间段内手动启动与定时启动共用该时间段已保存的随机收尾时间，不因再次点击开始延长工作时间。

## 3 执行计划和当日运行分离

### 3.1 计划

计划是用户保存的长期安排，状态包含启用、已停止和停用，以及配置版本。“已停止”允许编辑并阻止自动启动；自动间歇“等待时段”只是运行状态，自动间歇不清空进度。计划允许执行，不代表本地设备正在执行。

### 3.2 当日运行

通常一个计划在一个执行日期只有一个运行。同一日期因用户停止后重新启用，或用户在完成后明确再次开始，可以产生新的运行实例；每个实例有独立运行 ID。自动触发不能因重复轮询、重启或新时间段重复创建运行。

启动时先锁定计划，读取是否存在当天未结算运行：自动间歇接续原运行；用户停止的旧运行已结算，再启用从第一项新建。全部完成后定时器当天不会再次启动；用户明确再次开始才产生新实例。新实例建立后，后续时间段接续它，不另建一套自动运行。

每次用户停止后重新启用，或完成后明确再次开始，产生独立启用批次；同一批次内自动触发按计划、执行日期、启用批次去重。手动请求使用请求唯一编号。二者必须在同一计划级启动事务中检查当前运行与批次，再交由绑定设备申请本地执行锁，不能仅依靠两个互不相关的唯一键。连点或重试不能重复产生启用批次。

| 状态 | 含义 | 后续行为 |
| --- | --- | --- |
| 待执行 | 当天运行已建立，尚未进入时间段 | 到时开始 |
| 执行中 | 正在执行岗位或穿插消息动作 | 持续安排下一步 |
| 收尾中 | 到达随机结束时间，停止领取新操作 | 确认已发动作并保存进度 |
| 等待时段 | 当天还有后续工作时间 | 下个时间段继续 |
| 等待执行权 | 有其他任务或必要收尾占用页面 | 排队后延，在合法时间内取得执行权后开始 |
| 启动准备 | 已取得本地和云端执行权，正在准备页面 | 本地开始确认后进入执行中 |
| 用户停止 | 用户停止当前运行，旧运行结算 | 再次开始从第一执行项启动新运行 |
| 当日完成 | 全部岗位及当前待处理工作完成 | 定时器当天不重新启动；用户明确再次开始可新建运行 |
| 当日未完成 | 最后时段结束，仍有工作剩余 | 生成报告，未来日期照常运行 |
| 执行受阻 | 登录、权限、浏览器或数据异常 | 保存原因；不继续不确定动作 |

当天结束时将剩余工作结算到报告，结束该运行；不能把“等待时段”一直带到第二天。手动停用计划是独立用户操作。

### 3.3 当日执行项推进

进度按执行项 ID 保存，不只按岗位 ID 保存。同一岗位重复出现时，各项分别记录找简历主动作的状态、消息服务状态和成功数量。

- 找简历达到岗位单次成功打招呼上限，或原有扫描正常结束后，主动作完成。
- 当前待回复和已到期复打处理完后，可以推进到下一个岗位。
- 前面执行项已经勾选并激活的消息动作，在当日运行仍进行时继续接受消息检查和到期复打。
- 尚未开始的执行项不提前执行其动作。仅因同一岗位前面出现过，不能提前激活后面执行项的自动回复或复打。
- 因此，“先统一找简历，再统一回复”不会被后面尚未开始的回复执行项打断；若前面的执行项本身勾选了回复，则按该项设置处理。
- 同一账号、平台、岗位、消息动作只有一个活跃处理入口。重复执行项再次激活相同消息动作时，复用已有入口，并采用最近开始执行项的动作设置，不启动第二个发送循环。
- 仅选择消息动作的岗位，处理当前待回复和已到期复打后推进。
- 所有执行项推进完毕后，再检查已激活消息动作的当前消息和到期复打；没有待处理工作时完成当日运行，不为未来可能到期的人无限等待。
- “当前工作已清空”只表示本轮检查结果，不保证候选人之后不会再发消息。

## 4 三种动作的执行安排

### 4.1 主流程安排执行机会

计时和数据检查可以独立进行，但所有招聘页面的读取、切换、输入、点击由同一浏览器执行通道完成。后台计时器只登记到期任务，不能直接操作页面。

| 模式 | 通常安排 | 防止其他动作一直等待 |
| --- | --- | --- |
| 优先回复开启 | 待回复消息 → 到期复打 → 找简历打招呼 | 每批结束重新检查其他动作 |
| 优先回复关闭 | 找简历为主，定期穿插回复和复打 | 消息和到期复打不能等到找简历全部完成 |

第一版建议内部默认：消息检查间隔 60 秒；同类消息动作一批最多处理 3 人或占用 60 秒，到达其中一个边界后，在当前候选人安全收尾处让出机会。参数集中放在主流程配置，不散落各平台。60 秒不是硬中断，也不保证候选人在 60 秒内收到回复。

关闭优先回复时，检查时间到后同样安排消息批次；开启时，在安全边界提前处理已经发现的回复。到期复打等候超过一个消息检查周期时，下一次安全切换至少安排一位，避免新消息不断到来造成复打长期延后。

不同岗位间按待处理时间和等待时长分配机会。一次只切入一个岗位，进入后必须核对账号、平台和岗位，再处理候选人。

### 4.2 找简历打招呼

- 保留现有筛选、评分、详情识别、打招呼和数量限制逻辑。
- 在候选人处理边界支持让出执行机会，不重跑整个扫描流程。
- 处理完成的候选人按稳定标识去重，不依赖页面索引。
- Boss 推荐候选人使用卡片完整 data-geekid；聊天使用完整 data-id，两类标识分别保存，只有明确验证后才建立映射，不以姓名年龄推断。
- 切换前保存最近三个已处理候选人的 ID 与顺序、尚未处理队列和本次完成记录。回来先检查岗位和筛选条件，以及恢复位置的有序三个 ID；匹配时快速继续，不重新从头遍历。
- 不足三人检查已有锚点；零锚点、ID 或顺序变化、锚点缺失、筛选变化及无法核对时，才回到当前列表起点按本次处理记录重新扫描去重。最后处理者不在列表时不无限寻找。
- 三个 ID 匹配表示当前位置符合续跑条件，不证明整个页面没刷新。后续候选人仍核对当前 ID 和本次处理记录，结果未知时不能重发。
- 快速续跑不保证覆盖后来移动到锚点前的未处理者；保留效率优先方案，不在每次返回或完成前强制再从头扫描。回退扫描只保证在实际遍历范围内按本次记录检查。
- 当日自动间歇跨时段保留成功数量，不能因为工作时间段结束就重置单次上限；用户停止后重新开始属于新的单次执行。
- 同一岗位在不同执行项中再次执行打招呼时，是一次新的单次执行，各项分别应用岗位配置上限；同一执行项跨时段恢复不重置。候选人历史去重和平台已有额度限制始终保留。

### 4.3 自动回复

- 复用现有未读会话扫描、候选人上下文、AI 回复和回复后索要简历逻辑。
- 将整轮名单处理拆成有边界的批次，不在底层循环持续占用页面。
- 回复发送、发送结果确认和必要索要简历确认作为同一安全处理单元。
- 切换后重新核对消息上下文；候选人有新回复或草稿变化时重新判断，不能发送旧上下文生成的文本。
- 发送前必须核对唯一 selected 会话 ID 与预期 conversation_id 相同，并等待搜索后的状态更新；同名面板文字不作为唯一身份。
- 不把无数据、页面读取失败、登录失效统一当作没有待处理消息。

### 4.4 自动复打招呼

- 保留现有复打时间范围、最大次数、拒绝检测、AI 提示词和已收到简历等限制。
- 将上次成功打招呼或复打时间加随机间隔，得到该候选人的下次可复打时间。
- 随机间隔沿用个人配置，生成一次后持久化；页面切换、轮询和程序重启不重新抽样。
- 成功确认后才更新次数、上次时间和下一次时间；失败或结果不明不能直接当作成功，也不能盲目重发。
- 取消“处理完一人后阻塞等待几十分钟再处理下一人”的安排。每个人独立计时，等待期间继续其他动作。
- 复打前重新核对身份、最新消息、草稿、拒绝和简历状态。对方已经回复时转入回复流程。
- 优先按已验证的会话 ID 定位；推荐 ID 与聊天 ID 未验证映射时保留身份待核对，不能按姓名搜索顺序猜测目标。
- 消息字数沿用现有约束；开发时先核对真实校验入口。如原实现只依靠提示词，需要补明确校验，不自行编造字数上限。
- 历史候选人的到期时间已经过去时进入待检查队列，不因为今天新启动再额外推迟一个随机周期。

### 4.5 页面安全切换

切换顺序：当前候选人收尾 → 确认结果 → 关闭详情或弹窗 → 保存进度 → 进入目标页面 → 核对账号与岗位 → 重新读取候选人。

找简历、回复和复打不能各自保留一个可以同时操作页面的后台循环。计时器到期也不能在消息输入一半时抢占页面。

严格禁止 evaluate、evaluateHandle、$eval、$$eval、addScriptTag、addInitScript、dispatchEvent 等注入方式。只能使用标准 Page、Locator、鼠标、键盘、真实滚轮和截图。标准能力不足时向用户确认。

### 4.6 复打结果的可靠补传

目标是一次已确认复打只记一次次数，网络重试只补记录，不再次发消息。招聘平台没有提供可直接使用的发送事务，不能声称浏览器发送在任何崩溃下都能保证准确一次；结果不明时沿用待核对机制。

#### 本地发送和待补传记录

1. 沿用本地发送意图的独立 ID 作为 `operation_id`。真正发送前持久化该 ID、账号作用域、平台、岗位、候选人、运行与执行项，以及本次联系基准和复打次数。重启、重试、换执行项不生成新编号绕过旧意图。
2. 沿用 prepared → sending → sent 或 unknown 的状态控制。只有页面确认发送成功才能生成成功结果；unknown 不能当作成功，也不能直接重发。
3. 将本地状态改为 sent 和写入待补传结果放在同一个 SQLite 事务。结果包括 `operation_id`、实际发送确认时间、消息指纹、基准联系时间、复打前次数及必要报告字段。
4. 后台读取待补传记录，使用原编号和相同内容提交到云端。确认云端已经持久化该结果后才标记补传完成。
5. 网络失败或回执丢失时重试同一结果。参考退避为 5 秒、30 秒、2 分钟，之后最多每 5 分钟重试；重启仍能继续。权限失效时保留记录并等待重新登录，数据冲突时记录待核对，不无限重试错误内容。
6. 同一候选人有已发送待补传结果时，不依赖陈旧云端次数再创建下一次复打。其他候选人和计划工作可继续；补传本身不操作招聘页面，运行结束后也可继续。

崩溃发生在平台已发送但本地成功事务未提交时，发送意图保留 sending，并在重启时变为 unknown。只有页面能够可靠确认原发送时才补记成功和生成待补传结果；无法确认时保留待核对，不重新点击发送。

#### 云端只记账一次

- 扩展现有复打结果接口和存储方法，先复用再改造，不沿用当前每收到成功请求就直接加一的处理。
- 新增结果收据，至少保存团队与账号作用域、`operation_id`、业务内容摘要、候选人归属、实际发送确认时间及处理结果。团队作用域内 `operation_id` 唯一；同编号不同候选人、不同结果或不同内容必须拒绝。
- 在一个 PostgreSQL 事务中完成结果收据登记、锁定对应候选人、联系基准和复打前次数核对、次数更新，以及需要保存的业务事件。同一账号与候选人的同一复打基准也要限制重复成功，避免换一个编号重复记账。
- 同一编号再次上报，返回已经提交的原结果，不再次加次数、不重新生成事件、不改变联系时间。
- 首次成功按真实发送确认时间更新上次复打时间，不使用每次补传时的服务器当前时间；校验时间合理性，旧结果不得把较新的联系时间回退。
- 收据、次数或业务事件任何必需写入失败，都回滚事务。并发上报依靠唯一约束和候选人行锁保证最多一次更新。
- 诊断日志或通知失败不能在记账事务提交后把成功结果改成失败回执。需要可靠派生的日志或事件使用事务内待办记录，由后台补写并按原事件编号去重。
- 实际账号与候选人作用域必须从现有岗位和账号绑定校验，不能只信任客户端传来的账号摘要。
- 同一基准已有其他编号结果，或客户端次数落后且无法通过原收据核对时，返回明确冲突供核对，不能用覆盖最新次数的方式强行补记。
- 内存存储与数据库存储实现同一契约，测试不能只验证无去重的内存路径。

网络传递允许多次，云端记账只发生一次。发送去重、结果补传和计划启动去重是三种不同约束，不能用计划 ID 或运行 ID 代替每次发送编号。

## 5 时间段结束和次日规则

### 5.1 随机收尾

每个工作时间段生成一次 3–6 分钟随机延后量，按计划、日期和时间段起止值保存，并关联当日运行。设备重启、同一时段停止后再开始不得重新抽样；编辑后时间段起止值改变则为新的时间段。达到实际停止领取时间后不再开启新的候选人操作，只做已经开始动作的必要确认。

示例：上午名义结束为 12:00，本次抽样 4 分钟，则 12:04 开始收尾；下午 13:30 从当日保存的进度继续。

必要确认可能超过随机时间边界，不能为保证整点结束而让已发送消息失去结果记录。确认超时的动作保存为结果待核对。

### 5.2 时间冲突

保存时检查同一计划内的名义时间段不能重叠，不强制相邻时段间隔 6 分钟；不同计划允许时间相交。随机延后和必要收尾产生的实际占用冲突，由运行时执行权控制处理，不在配置阶段拒绝。

第一版复用本地程序单任务限制，计划和手动任务共用执行锁。开始前检查是否已有任务或收尾动作，检查和占用必须为同一个原子操作；不能先查空闲，再各自开始。云端已有账号运行限制与本地设备执行权都需要满足。

云端账号占用为手动任务与所有计划共用的独立记录，现有手动启动接口也接入该契约。请求排队不能将岗位或运行提前标成执行中。先取得本地预留，再在云端账号级事务锁内申请占用；两端许可确认后才准备并开始。云端忙或明确拒绝时释放本地预留，回执不明时查询原请求结果，核对前不操作页面。

父计划运行持有一个 owner_id 和占用凭证，执行项切换与已激活消息继承该占用；子项状态独立更新，不靠把旧岗位一直标为 running 保持排他。必要收尾完成后释放本地执行权，再以当前 owner_id 和凭证释放云端占用；旧释放不能清除新占用者。自动间歇释放占用但保留同一运行，下个时段重新领取。旧式正在执行的手动任务升级后仍视为占用，设备离线不直接授权抢占。

占用时只保存一份等待请求，不开始页面动作、不计执行数量、不停止当前任务。等待按原定触发时间先后排序，同时间按稳定请求顺序排序。执行权释放时立即检查队列，并保留默认 5 秒检查作为兜底；重复检查不能重新入队或让请求丢失原顺序。

后延遵守原计划的工作时间，不把时间段整体向后平移。等待到本时段名义结束仍未取得执行权时，转到当天后续有效时段；当天没有后续时段则记录未完成并报告，周期计划下个执行日从第一项开始。随机延后区间用于已开始任务收尾，不用于启动一个迟到的新任务。用户停止或停用后移除待执行请求。

日志记录进入等待、占用任务、原定与实际开始时间、等待时长、转到下个时段或当日未执行的原因。重复轮询保持安静，只在状态变化时记日志。不能只根据前端显示“已停止”判断页面空闲，必须等待必要收尾释放执行权。

### 5.3 最后时段结束

- 结束当日运行，记录完成和未完成岗位、动作、数量、原因以及剩余工作。
- 生成页面报告；用户已有可用邮件配置时发送同一份摘要。
- 报告失败单独记录并重试，不能因此停止未来计划。
- 正常完成也保留当日摘要；未完成必须明确提醒。
- 当日运行未完成、受阻或设备离线，都不能自动停用周期计划。

### 5.4 下个执行日

- 按周期创建新的当日运行，从岗位列表第一项开始。
- 新建岗位单次计数，不继承昨天的打招呼剩余额度或扫描游标。
- 保留候选人联系历史、累计复打次数、去重和结果待核对记录。
- 昨天剩余工作只保留在历史报告，不作为今天的岗位启动位置。
- 日末结算与次日启动需防重复；遗漏的昨天结算先补记，再创建今天运行，不能恢复昨天动作。

## 6 保存的数据

以下为逻辑模型，正式字段命名和表结构开发前先复用现有相似模型。所有新增数据库字段都要有中文备注。

| 数据 | 保存位置 | 核心内容 |
| --- | --- | --- |
| 执行计划 | 云端 | 团队、用户、设备绑定、名称、启用或已停止或停用、启用批次、时区、周期、有效日期、版本 |
| 时间段 | 云端 | 计划、开始时间、结束时间、顺序 |
| 岗位执行项 | 云端 | 独立执行项 ID、计划、岗位、顺序、动作集合、优先回复；岗位 ID 可重复 |
| 当日运行摘要 | 云端 | 独立运行 ID、执行日期、配置版本、启动来源、状态、各动作数量、结束原因、报告状态 |
| 云端账号占用 | 云端 | 已认证账号、占用者类型与 ID、绑定设备、占用凭证和状态；手动任务与计划共用 |
| 当日运行进度 | 本地 SQLite | 配置快照、当前执行项 ID、岗位、各执行项动作状态与计数、时间段随机结束时间 |
| 当日时段收尾记录 | 本地 SQLite | 计划、日期、时间段起止值、固定随机延后量；同日同一时间段多个运行共用 |
| 候选人复打安排 | 本地持久化并关联现有云端联系记录 | 账号作用域、平台、候选人、岗位、基准联系时间、次数、下次时间 |
| 发送记录 | 复用现有本地记录 | prepared、sending、sent、unknown 等发送状态及去重标识 |
| 复打待补传结果 | 本地 SQLite | operation_id、原发送归属、联系基准、发送确认时间、内容摘要、上报字段、补传状态与重试信息 |
| 复打结果收据 | 云端 | operation_id、已校验归属、原结果摘要、联系基准、计数结果、发送确认时间 |
| 报告发送记录 | 云端 | 当日运行、通知类型、接收人、发送状态、重试信息 |

去重约束至少覆盖：自动触发的计划加执行日期加启用批次、手动启动请求编号、报告加运行 ID 加通知类型加接收人、发送 operation_id、候选人联系基准对应的一次复打安排与成功结果。计划级启动事务和本地执行锁保证不同入口也不重复执行。配置版本和运行状态更新需要防止旧设备或旧请求覆盖新状态。

执行项 ID 独立唯一，不对“计划加岗位”建立唯一约束。候选人发送去重继续按账号、平台、候选人及消息或联系基准判断，不能加入执行项 ID 后让同一条消息被重复发送。历史统计保留实际执行项归属，不因同岗位新执行项开始而改写。

云端不保存页面焦点、滚动位置或 DOM 引用。候选人正文按现有数据边界处理，报告使用必要摘要。

## 7 接口和模块职责

### 7.1 云端后端

新增计划增删改查、停止确认、立马开始、按计划时间执行、启用停用、当日运行摘要、报告查询接口；复用现有身份、团队权限、岗位可访问性、设备绑定及邮件发送能力。

后端校验日期、时间冲突、动作平台能力、岗位归属和配置版本。后端存储与提供数据，不定时操作招聘网站，不承担本地岗位流程。

可采用 `/api/v1/execution-plans` 作为计划资源路径，具体路由要跟随现有项目命名。运行记录上报和通知要求幂等，复打成功上报失败需可靠补传，不能因此再次发送消息。

### 7.2 本地 Go

- 新建执行计划模块，负责日期计算、配置同步、运行唯一性、执行锁和日末结算。
- 新建或提取动作调度模块，负责回复优先、到期复打、批次边界及等待公平性。
- 由岗位执行器暴露可继续的小步骤，不从计划模块重复实现筛选和消息发送。
- 本地数据库保存检查点；设备重启或自动间歇按原运行继续，并核对登录、会员和平台能力。用户停止后再次开始从第一项新建运行，不恢复旧游标。
- 复用现有失败通知能力，但区分“计划未完成报告”和“岗位异常通知”。
- 统一收敛现有岗位结束后的后台简历检查，避免其绕开计划时间段或与页面执行锁冲突。

### 7.3 平台适配和 Node 工具

平台提供准备页面、选择并核对岗位、读取候选人和执行动作。通用模块不知道 Boss、猎聘等具体选择器。

Node 只接收具体操作请求，不计算周期、岗位优先级或候选人复打时间。保留零脚本注入约束。

### 7.4 前端

新增独立页面、计划表单、岗位排序组件、运行摘要及报告展示，并新增对应服务层。不要继续把全部新业务堆入现有岗位管理大文件。

平台不支持某动作时禁选并说明原因，本地启动时再次校验。旧本地程序不支持计划时提示更新，不能静默当作已经启用自动执行。

## 9 异常和恢复

- 登录失效、会员权限失效、岗位被删除或平台动作不支持时，保存明确原因，不把异常标记为完成。
- 设备重启时恢复当天已开始的运行；当前不在时间段内则等待，已经过日则只补结算报告。
- 电脑休眠或时钟跳变后重新计算当前时段，不连续补发错过的复打，也不执行往日计划。
- 消息发送结果不明时先核对，无法确认的候选人保持待核对状态，不直接重发。
- 本地已确认发送、云端上报失败时补传同一结果，不增加第二次发送。
- 停止操作只有本地确认安全收尾后才成为可编辑状态；网络失败时显示等待确认，不允许编辑与运行同时发生。
- 读取计划失败时不从过期配置新建运行；已开始运行使用既有快照，并继续原有权限与会话校验。
- 报告中区分无待处理数据、数量上限达成、时间不足、设备离线和执行异常。

## 10 开发步骤

开发采用两个里程碑，详细任务见[执行计划详细开发计划](执行计划详细开发计划.md)。**先完成单岗位自动回复、优先回复、运行期间定时消息检查、复打和安全动作切换，并独立测试验收；验收通过后才开发多岗位计划管理。** 多岗位计划表、计划接口和计划页面不得提前开发。

单岗位模块通过现有岗位开始入口使用，不要求创建执行计划。定时消息检查由本地程序在当前任务运行期间完成；按日期和工作时间段启动属于后续多岗位计划管理。

2. 提取单岗位安全执行步骤和回复、复打批次，保留现有发送确认与去重。
3. 增加动作调度和按候选人计时的复打安排，验证优先回复与公平切换；增加本地结果待补传队列和云端一次记账事务。
4. 将优先回复和定时消息检查接入现有单岗位入口，完成单岗位自动化测试与 Windows 场景验收，形成明确通过记录。
5. 单岗位验收通过后，增加云端计划模型、权限校验、冲突检查及运行摘要接口，复用已验收的岗位动作模块。
6. 增加多执行项、跨时段恢复、随机收尾与跨日结算，接入本地定时启动、立马开始、停止后编辑和启动去重。
7. 增加执行计划页面、岗位排序、动作配置、运行展示和报告发送。
8. 完成多岗位全流程验收并回归单岗位模块，再发布支持计划的本地程序版本。

新增代码文件写用途注释，新增业务方法写标准中文注释。数据库迁移编号从开发时真实状态顺延，不在 Spec 中冻结编号。

## 11 验收要求

| 场景 | 预期结果 |
| --- | --- |
| 一次性计划与每周计划 | 只在匹配日期触发，重复检查不重复创建运行 |
| 多岗位执行 | 找简历按岗位顺序推进，岗位无需配置独立时间 |
| 同一岗位多次添加 | 各执行项独立保存动作与顺序，不合并、不拒绝 |
| 先消息后找简历 | 前面消息项当前工作完成后进入同岗位找简历项，已激活消息按规则穿插 |
| 先统一找简历再回复 | 后面回复项开始前不提前激活，仅按前面执行项已勾选动作执行 |
| 同岗位重复消息动作 | 共用一个活跃处理入口，不重复发送，不改写历史执行项统计 |
| 同岗位重复打招呼与午间续跑 | 新执行项独立计算单次上限，同一执行项跨时段不重置，历史去重仍有效 |
| 优先回复开启 | 找简历未结束时可安全切入回复，然后继续找简历 |
| 优先回复关闭 | 找简历为主，但消息和到期复打仍能定期处理 |
| 消息持续增加 | 找简历和复打不会长期得不到执行机会 |
| 前面岗位出现消息 | 后续岗位运行时仍可穿插处理，切换前核对岗位 |
| 两位候选人不同复打时间 | 分别按各自到期时间进入队列，不因前一人等待阻塞后一人 |
| 复打候选人已经回复 | 不再复打，按勾选动作进入回复处理或跳过 |
| 自动间歇或设备重启 | 同一人的随机到期时间和本时段随机收尾时间不重新生成 |
| 午间间歇 | 下个时间段从未完成工作继续，当日打招呼计数不重置 |
| 推荐页三锚点匹配 | 从保存位置快速继续，不从头遍历，后续按本次记录轻量去重 |
| 三锚点不变但前方有新候选人 | 快速路径不承诺全列表无遗漏，不追加强制核查，不误报覆盖范围 |
| 推荐页锚点不匹配或缺失 | 从当前列表起点去重扫描，不依赖旧序号，不无限找旧人 |
| 同名会话及异步选中 | 按实际会话 ID 核对，旧选中或身份不明时不发送 |
| 最后时段未完成 | 保存日志、生成报告，计划仍启用 |
| 下个执行日 | 从第一岗位新开始，单次计数重置，候选人历史不清零 |
| 全部提前完成 | 当日结束，不在后续时段重复启动，也不无限等待未来复打 |
| 编辑执行中或收尾中计划 | 前端禁止编辑，后端也拒绝保存；先停止并确认收尾 |
| 停止后不编辑再次开始 | 旧运行已结束，新运行从第一项开始，保留联系历史和待补传结果 |
| 停止后编辑并重新启动 | 新运行采用新版本，从第一项开始，不套用旧游标 |
| 保存后选择按计划时间执行 | 重新启用定时触发，不因保存动作直接开始 |
| 手动开始与定时同时发生 | 使用同一运行，页面只执行一份任务 |
| 连点开始或开始回执丢失 | 相同请求返回原运行，不重复初始化计数 |
| 时间段外点击立马开始 | 等待下个匹配时间段，不操作招聘页面 |
| 收尾期间点击立马开始 | 不开启新一轮，也不延长已保存的随机结束时间 |
| 发送结果不明 | 不直接重发，保留待核对状态 |
| 云端上报失败 | 补传原结果，不再发送一次消息 |
| 云端已提交但回执丢失 | 原编号补传返回原结果，次数和事件只增加一次 |
| 本地确认成功后立即崩溃 | sent 与待补传结果同时落库，重启后可补传 |
| 平台发送后本地尚未确认就崩溃 | 恢复为 unknown，核对前不重发、不加次数 |
| 同结果并发补传 | 唯一收据与候选人锁保证只记账一次 |
| 同编号不同内容或换编号重复基准 | 拒绝冲突，不重复计数、不覆盖原结果 |
| 云端事务任一必需写入失败 | 收据、次数和事件一起回滚，可用原编号重试 |
| 诊断日志失败或迟到补传 | 不反转已提交回执，不重复事件，不重置或回退联系时间 |
| 同一计划时间段重叠 | 按名义时间拒绝重叠，不强制额外 6 分钟间隔 |
| 多计划同时间触发 | 允许保存，运行时原子取得执行权，其余排队后延并记日志 |
| 计划与手动任务争用 | 云端统一账号占用，本地统一页面执行权，等待任务不提前标为执行中 |
| 子项切换与自动间歇 | 子项继承父占用；间歇安全释放后，下个时段重领同一运行 |
| 旧释放或释放失败 | 凭证匹配才释放，迟到请求不清除新占用，失败时下个任务继续等待 |
| 后延超过当前工作时间 | 等待下个有效时段；当天无后续时段则报告未执行，不越过时间段启动 |
| 当前任务正在收尾 | 继续视为占用，收尾释放后才能开始下一任务 |
| 邮件失败 | 页面报告保留，通知可重试，周期运行不受影响 |
| 设备离线跨日 | 往日只记未执行或未完成报告，今天从第一岗位开始 |
| 不支持的平台动作 | 前端说明并限制，运行端再次拒绝，不隐式兜底 |

时间和调度使用可控时钟、可控随机源测试，不靠实际等待数十分钟。浏览器验收使用标准 Page、Locator 和真实鼠标键盘操作，验证不同页面切换后没有错人、重复发送或越过时间段操作。静态测试通过与真实招聘页面验收分别记录。

## 12 第一版边界

- 不新增各动作结束数量，不新增每个岗位的独立执行时间。
- 不实现同时操作多个岗位或浏览器页面。
- 不承诺关机、离线时操作招聘网站，也不提供云端代跑。
- 不无限等待未来新回复或未来复打，使计划无法完成。
- 不清空历史候选人状态来实现次日新一轮。
- 不将当日未完成转成计划暂停或停用。
- 不扩大已有平台动作支持范围，不回退到脚本注入。
