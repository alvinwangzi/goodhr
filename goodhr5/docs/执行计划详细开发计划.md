# HRPlus 执行计划详细开发计划

日期：2026-10-08

依据：[执行计划实现 Spec](执行计划实现Spec.md)。本文用于安排开发，不表示以下任务已经完成。产品行为以用户最新确认和 Spec 为准；工程细节在本文中落实为具体任务。

目标是让 HR 编排多个岗位及其动作，由 Windows 本地程序定时执行。实现必须覆盖安全切换、独立复打计时、跨时间段进度继续、停止后从头开始，以及可靠的结果补传。

开发顺序分成两个里程碑：**M1 先完成单岗位消息与动作调度，并独立测试验收；M1 验收通过后，才进入 M2 多岗位计划管理。** 不提前开发多岗位计划表、计划接口、计划页面或岗位编排。

M1 的“定时回复”指单岗位运行期间按间隔检查新消息、安排回复；按日期和工作时间段自动启动属于 M2。M1 通过现有岗位开始入口使用，不要求用户先创建执行计划。

本次更新纳入[Boss 候选人身份页面检查记录](Boss候选人身份页面检查记录.md)：真实 ID 核对、三个候选人锚点快速续跑、列表变化后的按 ID 去重，以及任务占用时排队后延。页面检查是方案依据，不代表业务模块已经实现或验收。

## 1 开发基线与规则

### 1.1 必须保留的产品行为

1. 一次性、每天、每周指定日期；每天允许多个不重叠时间段。
2. 岗位按执行项顺序处理，不设置单独的岗位时间。同一岗位允许多次添加，各项独立勾选打招呼、自动回复和自动复打招呼。
3. 优先回复在已激活的回复动作内生效；复打按每个人的到期时间检查，不等待回复全部结束。
4. 后面尚未开始的动作不能提前激活。前面已经激活的消息动作可在后续执行项期间穿插处理。
5. 第一版不增加结束数量输入。打招呼沿用岗位单次上限；消息动作按当前待处理工作推进。
6. 所有执行项和当前待处理工作完成就结束，不长期挂着等待未来消息。
7. 当天自动跨时段继续原进度；时段结束随机延后 3–6 分钟收尾。
8. 最后时段未完成，只记录日志和报告，周期计划仍启用；下个执行日从第一项重新开始。
9. 先停止，确认安全收尾后才允许编辑。停止后无论是否编辑，再次开始都从第一项新建运行。
10. 立马开始只在计划允许的日期及名义时间段内执行，其他时间启用计划并等待定时触发。
11. 单次执行计数可以重置；候选人联系历史、复打次数、去重和待补传记录不能清零。
12. 招聘页面零脚本注入；只用标准页面、定位器、鼠标、键盘、真实滚轮和截图。
13. 推荐页与沟通页来回切换，先核对最近三个已处理候选人的 ID 与顺序；核对通过快速续跑，核对失败才从列表起点按已处理记录恢复。
14. 同一设备任务开始前原子检查并取得执行权；占用时后延并记日志，正在收尾也算占用，不能越过配置时间段启动新任务。

### 1.2 本开发计划采用的工程默认值

其中前两项尚未收到用户单独选择，先按以下默认值安排；不改变已经确认的规则。

- **本地独立执行**：关闭 HRPlus 网页后，只要本地程序仍运行且登录有效，定时执行继续；程序重启后可恢复安排。新增受 Windows 当前用户保护的本地登录会话。
- **故障分级**：单执行项失败且页面清理成功时，记录失败并继续后续项；登录、会员、设备、浏览器或本地存储整体故障结束本次运行，保存报告，不停用未来周期。
- 时区为 Asia/Shanghai；第一版不支持跨午夜时间段。
- 一个本地程序一次只持有一个招聘页面执行权，手动任务与计划共用。
- 周期检查默认每 5 秒执行一次，计划同步每 30 秒一次；启动、停止和重新登录后立即检查，不依赖网页计时器。
- 消息检查默认 60 秒；消息一批最多 3 人或占用 60 秒，在候选人安全边界让出执行机会。
- 同一计划内按名义时间校验时段不重叠，不强制留出 6 分钟；不同计划允许相同时间触发，实际占用由执行权与等待队列解决。
- 页面运行状态每 2 秒刷新，非运行列表每 10 秒刷新；页面不可见时降低刷新频率，不影响本地调度。
- 优先复用已有 Go、SQLite、PostgreSQL、MUI 和浏览器工具依赖，不新增队列服务或调度平台。
- 第一版沿用现有浏览器 Profile 与平台登录方式，不增加新的多招聘账号管理功能。不同平台和动作按现有能力开放，不把不支持的动作显示为可执行。

### 1.3 已核对的代码事实

| 现状 | 对开发的影响 |
| --- | --- |
| 云端业务路由采用 `/api/...` | 新计划云端接口跟随此风格，不照搬 Spec 中示意的版本前缀 |
| 本地路由采用 `/api/v1/...` | 计划控制放在本地路由，页面操作继续由本地执行 |
| 三种动作已有实现，但主流程按整段顺序执行 | 提取可继续的小步骤，不能只在外面套一个定时器 |
| 运行器内存状态主要按岗位 ID 保存 | 计划运行、执行项和历史消息动作必须有独立身份 |
| 本地 SQLite 使用单数据库连接 | 新事务中不能再调用使用普通连接的存储方法，避免互相等待 |
| 复打记录已有发送意图，云端成功上报会直接增加次数 | 保留发送保护，增加原子成功记录及云端收据 |

| 任务记录按岗位启动产生记录 | 计划新增父运行，原岗位任务记录作为子记录或关联记录 |
| 迁移目录当前已有 0097 | 开发时重新核对最大编号，追加迁移，不覆盖旧迁移 |
| 前端使用 AdminApp、AdminDialog、ChoiceCards、AdminUI | 新页面复用后台布局与表单组件，遵循会员主题变量 |

## 2 模块、状态和接口

### 2.1 职责分工

| 模块 | 负责 | 输出 |
| --- | --- | --- |
| 云端计划服务 | 计划保存、权限、启用批次、开始请求去重、运行记录与报告 | 计划快照、运行许可、状态与报告 |
| 本地计划管理器 | 同步、时间判断、启动、自动间歇、跨日与结束 | 当前计划运行和下一次安排 |
| 本地动作调度器 | 选择下个执行项或消息动作、处理公平性 | 一次安全动作请求 |
| 岗位执行器 | 复用筛选与沟通流程，执行小步骤并保存结果 | 可继续的检查点和动作结果 |
| 平台适配 | 准备页面、核对岗位与候选人、具体平台操作 | 页面事实和操作结果 |
| Node Worker | 标准浏览器读取与具体操作 | 原子操作结果，不决定招聘业务流程 |
| 本地补传器 | 从持久化队列提交已经确定的结果 | 云端确认或明确冲突 |
| 前端计划页面 | 编排、开始、停止、状态和报告 | 配置与用户明确操作 |

M1 先提取独立的 `actiondispatch` 与岗位小步骤、消息检查点及补传模块；M2 再增加 `executionplan` 和 `sessionstore`。岗位执行器继续持有平台实现，计划模块通过已验收的小步骤调用，不重复写浏览器流程。复打补传模块可作为 cloudapi 与 localdb 的独立组合，不堆进主 HTTP 服务文件。

### 2.2 必须区分的身份

| 身份 | 用途 |
| --- | --- |
| `plan_id` | 长期计划 |
| `config_version` | 本次保存的编排版本 |
| `activation_id` | 一次明确启用；停止后重启或完成后再次开始产生新批次 |
| `plan_run_id` | 一次实际计划运行 |
| `item_id` | 编排中的一条执行项；同岗位多次添加时不能相同 |
| `item_run_id` | 某次运行中的执行项实例 |
| `task_run_id` | 与已有岗位任务记录关联 |
| `operation_id` | 一次候选人发送意图及其结果；补传保持不变 |
| `request_id` | 一次明确开始或停止请求；网络重试保持不变 |
| `recommendation_candidate_id` | 推荐卡片读取的完整 data-geekid，保留来源与账号作用域 |
| `conversation_id` | 聊天列表读取的完整 data-id，保留后缀，不推断其含义 |

计划启动去重、消息发送去重和结果补传去重分别实现。不得用岗位 ID 同时代替执行项、运行和发送身份。

两类候选人标识分开存储，以明确验证的映射关联；映射状态为 verified、unresolved 或 conflict。旧姓名年龄标识保留 legacy 来源，不能自动改成真实平台标识。同名搜索顺序、年龄、公司及学校不作为 verified 映射依据。

### 2.3 状态与转换

计划状态：`enabled`、`stopped`、`disabled`。另有停止请求处理中标记，尚未确认停止时禁止编辑。

运行状态：`pending`、`waiting_resource`、`starting`、`running`、`draining`、`waiting_window`、`completed`、`incomplete`、`stopped`、`blocked`。`waiting_resource` 表示因其他任务或收尾占用而后延，不是执行失败；`starting` 表示已经取得两端执行权，尚在准备页面；本地确认实际开始后才变为 running。`blocked` 保存整体故障原因。最后时段结算后该运行不自动恢复，未来日期可正常创建新运行。

执行项状态：`pending`、`running`、`completed`、`failed`、`stopped`。消息动作激活情况单独保存，不以执行项 completed 推断消息服务已经解除。

关键转换：

- 正常自动间歇：running → draining → waiting_window → running，保持同一 plan_run_id 与计数。
- 任务全部完成：running → completed，当天定时器不重新开始本批次。
- 日末未完成：running → draining → incomplete，计划仍 enabled。
- 用户停止：先持久登记停止意图，禁止新动作，再 draining → stopped；计划变为 stopped。
- 再次开始：重新启用并产生新 activation_id 与 plan_run_id，从第一项开始。
- 执行整体受阻：running → blocked，完成必要收尾和报告，不继续同次计划。

停止、编辑、启用和启动更新都使用配置版本与状态比较，避免旧网页、旧设备消息覆盖新状态。

### 2.4 云端接口清单

本节计划接口全部属于 M2。M1 只改造已有复打结果接口及其收据，不新增计划管理接口。

路由遵循现有 `/api/` 风格，统一复用现有鉴权和错误返回。

| 接口 | 方法 | 主要输入 | 主要行为 |
| --- | --- | --- | --- |
| `/api/execution-plans` | GET | 分页、状态 | 查询当前权限范围的计划 |
| `/api/execution-plans` | POST | 基础信息、周期、时段、执行项、设备 | 创建计划；默认 stopped，保存不自动运行 |
| `/api/execution-plans/{id}` | GET | 计划 ID | 详情、配置版本、当前运行摘要 |
| `/api/execution-plans/{id}` | PUT | expected_version、完整配置 | 无进行中运行或已确认停止才保存 |
| `/api/execution-plans/{id}` | DELETE | expected_version | 无进行中运行才删除，保留历史运行与报告 |
| `/api/execution-plans/{id}/arm` | POST | request_id、expected_version、启动方式 | 启用并返回 activation_id；由本地判断立即执行或等待 |
| `/api/execution-plans/{id}/stop` | POST | request_id、当前运行 ID | 登记停止意图，关闭未来触发，等待设备确认 |
| `/api/execution-plan-runs/claim` | POST | 计划、批次、日期、设备、request_id、本地预留确认 | 共用账号事务锁领取占用，返回 starting 许可或原请求结果 |
| `/api/execution-plan-runs/{id}/status` | POST | 递增状态序号、状态、执行项摘要 | 接收来自绑定设备的单调状态，拒绝迟到覆盖 |
| `/api/execution-plan-runs/{id}/release` | POST | owner_id、占用凭证、收尾确认、request_id | 匹配当前占用后释放；旧凭证不能释放新运行 |
| `/api/execution-plan-runs/{id}/finish` | POST | 结束编号、结果、执行项统计 | 幂等结算并生成报告待办 |
| `/api/execution-plans/{id}/runs` | GET | 分页、日期 | 历史运行与报告摘要 |
| `/api/execution-plan-runs/{id}` | GET | 运行 ID | 执行项、动作统计、原因与报告详情 |

原有复打结果接口增加成功上报的 operation_id、基准次数、基准联系时间、实际发送确认时间、消息摘要及执行项归属。旧客户端暂保留现有入口，不宣称支持新的可靠补传契约；新客户端必须使用新字段并通过 capability 校验。

服务端只登记用户意图、验证及保存运行；招聘日期计算、是否进入时段以及页面动作仍由本地 Go 决定。

### 2.5 本地接口清单

下表的后台会话持久化和计划接口属于 M2。M1 在现有岗位开始参数中增加 `prioritize_reply`，默认 false；保留 `task_type`、既有开始、停止和状态接口，并返回单岗位当前动作、消息检查时间及分动作统计。

M1 增加 `cooperative_actions` 能力标志，前端只有明确支持时才允许使用优先回复和定时消息检查。M2 再增加计划相关能力标志，不能把 M1 版本显示成已经支持执行计划。

| 接口 | 方法 | 行为 |
| --- | --- | --- |
| `/api/v1/session/bind` | POST | 复用绑定，成功后更新当前用户受保护会话 |
| `/api/v1/session/unbind` | POST | 核对当前会话后清除本地凭证，停止该会话的新执行 |
| `/api/v1/local/execution-plans/sync` | POST | 立即同步允许在本设备运行的计划 |
| `/api/v1/local/execution-plans/{id}/start` | POST | 明确立即开始意图；合法时间内开始，否则等待 |
| `/api/v1/local/execution-plans/{id}/arm` | POST | 按计划时间执行，恢复自动触发 |
| `/api/v1/local/execution-plans/{id}/stop` | POST | 安全停止并提交云端停止确认 |
| `/api/v1/local/execution-plans/{id}/status` | GET | 当前执行项、动作、计数、下一时段与停止确认 |

本地接口接受 plan_id、expected_version、request_id，不接受前端任意传入一套未保存的编排绕过云端校验。开始和停止应快速返回请求已受理，再由状态查询展示完成情况，避免长 HTTP 超时造成重复点击。

`/health` capabilities 增加 `execution_plan`、`execution_plan_schema_version`、`re_greet_result_receipt`。前端只有明确支持才开放执行。

### 2.6 最小业务类型

M1 新增 `ActionStepRequest`、`ActionStepResult`、`SinglePositionRunContext`、`CandidateIdentityRef`、`RecommendationCheckpoint`、`ReGreetSchedule`、`ReGreetResultReceipt`；M2 再新增 `ExecutionPlan`、`PlanSchedule`、`PlanItem`、`PlanRun`、`PlanItemRun`。

M1 小步骤输入包含现有 task_run_id、本地单岗位运行 ID、岗位快照、动作、检查点和取消信号；输出包含是否有剩余工作、完成数量增量、下一次可执行时间、检查点与稳定错误类别。M2 通过可选关联上下文增加 plan_run_id、item_run_id；没有这些字段时 M1 必须正常运行，不创建虚假的计划或执行项记录。

小步骤只返回执行结果，不直接把整个岗位或计划标为完成。M1 由单岗位运行器更新整体状态，M2 由计划管理器更新计划状态。继续使用既有 Runtime、AutoReplyRuntime、ReGreetRuntime 接口，不要求无消息能力的平台实现空方法。

候选人定位接口从仅接收 name 改为接收 CandidateIdentityRef，包含预期 conversation_id、可用的 recommendation_candidate_id、账号作用域和辅助姓名。RecommendationCheckpoint 保存最近三个处理完的 ID、顺序、剩余队列、本次处理结果及成功数量；M1 不依赖计划身份。

### 2.7 云端账号占用与本地页面执行权

本节统一占用契约属于 M2；M1 继续使用已有账号启动检查与本地 browserLease，不以新计划存储为前置条件。

- 云端以已认证的 HRPlus 账号为占用范围，手动岗位和所有计划共用一个占用记录。所有入口采用相同账号事务锁，不能只锁 plan_id。
- 占用者为一次手动 TaskRun，或一次完整 plan_run_id；记录绑定设备、owner_id 和独立占用凭证。重复请求返回原占用结果，不产生第二个运行。
- 排队请求可以登记为 pending 或 waiting_resource，但不能占用账号、标为 running、写实际开始时间或初始化执行数量。
- 启动顺序固定为：登记请求 → 原子预留本地页面执行权 → 云端账号级事务申请占用并登记 starting → 核对许可后本地准备并开始 → 提交 running 确认。
- 本地忙时直接排队，不先把云端任务标为开始；云端忙或明确拒绝时释放本地预留并排队。许可回执不明时按原请求查询占用结果，核对前不操作页面。
- 现有 ClaimPositionStart 和手动启动接口必须接入相同占用契约。旧客户端通过原接口启动也会被新服务端统一检查；既有 positions.status 作为岗位状态显示，不能作为唯一账号占用依据。
- 计划运行期间，执行项和已激活消息动作继承同一 plan_run_id 的占用凭证，不另抢账号锁。切换岗位不释放父计划占用，也不按上一岗位 running 状态把同一计划的下一项挡住。
- 执行项的准备、运行和结束更新各自 TaskRun 与岗位展示状态；前面已完成项的穿插消息保留原任务归属。不得靠把全部前面岗位一直标为 running 来保护父计划。
- 只有页面清理和必要发送确认完成后，才能释放本地执行权。随后以 owner_id 和占用凭证匹配释放云端占用；本地已空闲但云端释放未确认时，下个请求仍等待云端许可。
- 自动等待下一时段时释放两端占用，保留同一 plan_run_id 与进度；下个时段重新取得两端执行权。用户停止、正常完成、日末结束或整体故障也按安全收尾后释放。
- 迟到的旧释放请求不能清除新占用者；设备离线或心跳过期不直接视为页面已经停止。重连先核对旧运行和凭证，完成收尾或确认本地旧运行不存在后再释放，不以强行清空 running 状态抢占。
- 升级时若已有旧式手动岗位运行，继续视为占用直到核对其结束，不能因为它尚无新占用记录就允许另一个任务开始。

#### S1-05 找简历扫描检查点

**依赖：** S1-03。

**开发内容：**

- 将“已读取候选人队列”“已完成稳定标识”“本次成功打招呼数量”分开保存。

- 不把 DOM 引用、元素下标、滚动位置当成可跨切换恢复的身份。
- 切换前保存最近三个已处理候选人的完整 data-geekid 及顺序，连同本次完成集合、尚未处理队列和计数一起持久化。不足三人保存已有一至两人；零人时没有可用锚点。
- 回到推荐页先核对岗位和筛选条件，只读取恢复位置对应的三个卡片 ID，检查数量、完整值、顺序及相邻关系。旧位置可作读取提示，但身份判断只以 ID 为准；正常路径不从头逐人核对全部历史列表。
- 三个锚点全部匹配且检查点完整时，保留本次队列与计数，从最后处理者后继续。每个后续候选人仍做一次轻量本次处理记录查询，并在真正操作前核对当前卡片 ID。
- 少于三人时须与保存的全部已有锚点匹配；岗位、筛选条件变化，缺锚点，读取失败，ID、顺序或相邻关系不一致时，禁用快速路径。
- 回退路径通过真实滚轮回到当前列表起点，按本次已完成 ID 集合重新检查：完成或明确跳过则越过，未完成则处理，retry_pending 按重试规则，unknown 先核对，不能重复发送。
- 找不到最后处理者也进入回退路径，不无限寻找旧人；列表重排后不能直接跳过旧锚点之前的未处理候选人。
- 锚点匹配只表示当前位置符合快速续跑条件，不记录为“整个页面确定没刷新”。三个 ID 不证明所有未加载候选人的完整顺序。
- 快速路径不保证发现已经重新排到锚点前的未处理者；第一版保持用户选择的效率优先方案，不在每次返回或完成前追加强制从头核查。仅回退路径对实际重新遍历的范围检查遗漏。
- 两条路径分别记录 resume_anchor_match 或 resume_rescan，以及回退原因；每次切换记录一次，不为每个已处理卡片刷恢复日志。
- 数量上限以已确认成功为准。同一岗位从找简历切到消息再回来时保持单次数量；用户停止后重新开始使用新的单次数量。M2 再接入自动跨时段与重复执行项语义。
- 既有工作休息策略接入同一停止和消息到期检查，不在长时间等待时忽略用户停止或定时回复机会。工作时间段结束检查在 M2 接入。
- 扫描正常结束保留原因，例如数量上限、无更多候选人；页面读取失败不当作空名单。

**验收：** 三个锚点匹配时从核对位置继续，不从头扫描，后续处理不重发；任一锚点变化、丢失或无序则回退去重；仅有一至两人时按已有锚点检查；最后处理者缺失时不死循环。两条路径均保留本次成功计数；回退路径处理实际重新遍历到的未处理者。快速路径不承诺覆盖锚点前后来出现的全部候选人。

#### S1-06 独立复打到期安排

**依赖：** S1-03、S1-02。

**开发内容：**

- 从现有复打候选名单读取已确认联系时间及次数，生成稳定的 per-candidate due_at。
- 随机间隔只在新的联系基准下生成一次，保存后沿用。确认发送后才改变基准并生成下一轮到期时间。
- 旧候选人缺少安排时，以原联系时间加抽样间隔建立，不以“今天启动时间”计算。
- 取消“发给一人后阻塞等待几十分钟再处理下一位”。等待期间返回给调度器。
- 查找候选人后重新确认当前会话与岗位、最新消息、拒绝及简历状态。
- 复打以已验证 conversation_id 定位；推荐 data-geekid 必须通过 verified 映射关联。搜索后同名面板与旧 selected 都不能代替 ID 核对，身份未确认时不发送或增加复打次数。
- 发前校验 200 个 Unicode 字符上限，复用现有复打限制；不截断后直接发送，超限记录原因。
- 已回复候选人由已激活的自动回复处理；未勾选回复时只记录跳过，不替用户开启动作。
- 复打最大次数、时间范围和拒绝开关继续来自现有个人与岗位配置。

**验收：** 张三 9:38、李四 9:42 到期各自进入队列；重启不改变到期时间；候选人回复后不再复打；次数限制仍有效。

#### S1-07 复打结果云端一次记账

**依赖：** S1-02；直接复用已有岗位、团队、设备和候选人归属校验，不依赖计划 Service。

**开发内容：**

- 将复打成功请求扩展为有 operation_id 的结果契约，按实际归属核对账号与候选人。
- 对照存储中已有联系基准及次数，避免客户端用新编号重记同一次成功。
- 在同一个 PostgreSQL 事务中插入结果收据、锁候选人、更新次数和真实发送时间、写必要业务事件。
- 事务中的所有方法使用传入的事务对象，不把独立 db 方法拼在事务外。
- 已提交的原编号直接返回原结果；同编号不同内容明确冲突。
- 收据的候选人、实际发送时间、消息指纹和基准内容都参与摘要；重试时间、重试次数不参与。
- 用发送确认时间更新联系事实，补传时间仅记为 received_at。迟到请求不能回退最新联系时间。
- 日志或通知失败使用持久待办重试，不能在核心事务提交后返回“整个成功结果未保存”。
- 内存实现同样需要收据及基准去重；历史旧客户端保留兼容。M1 新复打路径使用可靠收据接口，M2 复用同一实现。

**验收：** 原编号串行、并发和丢回执重试都只加一次；任一必需写入失败全部回滚；换编号同基准不能加第二次；不能跨用户或候选人使用编号。

#### S1-08 本地原子成功记录与补传器

**依赖：** S1-07、S1-06。

**开发内容：**

- 发送前保存原 operation_id 和发送意图，继续使用现有 sending/unknown 禁止盲目重发。
- 页面确认成功后，使用同一个 SQLite 事务更新 sent 并创建待补传结果；事务内部不重新使用普通连接查询。
- 补传结果保存原始身份、实际发送时间、基准次数、联系时间、摘要与必要报告内容，重试不重新生成 AI 消息。
- 云端确认 receipt 后才标记 acked；丢回执按原编号补传。
- 退避为 5 秒、30 秒、2 分钟、后续每 5 分钟；持久保存 next_retry_at。
- 网络类错误重试；登录过期等待重新登录；内容和基准冲突标记需要核对。
- 该候选人的未确认上报阻止其下一次复打，其他候选人可继续。
- 补传工作独立于浏览器租约，在任务完成、用户停止和网页关闭后仍可处理。
- 历史已 sent 但未上报的旧版本记录不自动编造完整收据；仅在具备原始基准与发送证据时补记，否则列为待核对。

**验收：** 成功后立即重启仍能补传；服务器已提交但客户端未收到时只记一次；unknown 不生成虚假成功；本地事务失败不出现 sent 却无补传记录。

#### S1-09 单岗位优先回复与定时动作调度

**依赖：** S1-03 至 S1-08。

**开发内容：**

- 先以一个岗位和一个 TaskRun 运行，不创建计划、执行项或多个岗位服务表。
- 复用 browserLease，让找简历、回复、复打和原有后台索要检查共用页面执行权。
- 加入可替换 Clock 与计时器，首次运行先检查已勾选的消息动作，之后默认每 60 秒检查新消息；计时器只登记待检查，不直接操作页面。
- 定时消息检查不能等到扫描全部结束；每个候选人安全收尾后检查是否应让出机会。
- prioritize_reply 开启时，已发现回复先处理，再处理到期复打，再继续找简历；关闭时以找简历为主，但消息检查到期仍安排批次。
- 回复批次最多 3 人或 60 秒，复打同样分批；到期复打等待超过一个检查周期，下一次安全切换至少安排一人。
- 找简历还有工作时，连续两个消息批次后至少让出一次找简历机会。
- 复打按人计时，等待时执行其他动作，不阻塞等待几十分钟。
- 切换前完成当前候选人操作与发送确认，关闭详情，再核对当前岗位和候选人；不能同时启动多个页面循环。
- 推荐页返回使用 S1-05 的三锚点快速路径，失败才走重新扫描；不为了每个消息检查周期重复遍历历史候选人。
- 有找简历剩余工作时，当前没有未读消息不代表整个岗位结束。全部已选动作当前工作完成后结束本次任务，不长期值守。
- 原有后台索要简历检查并入该调度，不能在主动作切换期间独占另一个页面通道。
- 停止命令不再领取新候选人，已经开始发送的动作完成必要确认或保留 unknown 后结束。
- M2 仅在此已验收调度器上增加多执行项上下文及多个已激活消息岗位，不能再实现一套三动作调度逻辑。

**交付：** 从现有岗位开始入口即可运行的独立动作调度模块。

**验收：** 找简历未结束时能及时回复；新消息和到期复打能穿插；找简历、回复和复打不会互相长期阻塞；单岗位停止后没有残留页面操作。

#### S2-01 新增云端与本地数据模型

**依赖：** S1-11 验收通过。

**云端数据：**

- execution_plans：所有者、团队、设备、名称、状态、配置版本、启用批次、周期、时区和停止意图。
- execution_plan_windows：时间段起止值和顺序；不允许结束早于开始。
- execution_plan_items：独立 item_id、岗位、顺序、动作集合、优先回复；禁止建立“计划加岗位”的唯一约束。
- execution_plan_runs：独立运行 ID、日期、批次、快照、状态与状态序号、开始及结束时间、结束原因。
- execution_plan_item_runs：本次执行项、关联 task_run_id、各动作数量和结果。
- execution_plan_requests：明确开始和停止请求编号及原返回结果。
- account_execution_owners：账号、绑定设备、占用者类型及 ID、占用凭证和状态；手动任务与计划共用，账号范围内仅一个当前占用者。
- execution_plan_reports：运行、报告摘要、通知状态和重试信息。
- re_greet_result_receipts 已由 M1 交付，M2 复用并增加可选计划归属，不重复创建另一套收据。

**本地数据：**

- 计划配置缓存、运行检查点、执行项进度、已激活消息动作。
- 任务等待队列：请求编号、原触发时间、稳定序号、计划和启用批次、有效时段、当前占用任务和等待状态；同一请求只保存一份。
- 按计划、日期、时间段起止值保存随机收尾时间，避免同一时段重新开始后抽样变更。
- 按账号作用域、平台、候选人及联系基准的复打安排已由 M1 保存，M2 只关联计划运行上下文。
- 复用 M1 复打待补传队列；新增计划状态及结算待补传队列。
- 本地登录会话的受保护内容与必要用户、设备标识；不得把 Token 放在运行快照或日志。

**数据库约束：**

- 自动运行唯一性包含计划、日期和启用批次；用户明确重启允许新批次。
- 收据的团队加 operation_id 唯一；同候选人同联系基准重复成功受约束。
- 时间段和执行项排序唯一且连续，修改通过事务提交，不暴露半套配置。
- 为设备计划同步、计划状态待补传及历史运行查询建立必要索引；复打 due_at 和结果队列索引复用 M1。
- PostgreSQL 字段加 COMMENT；SQLite 建表及新增字段保留中文说明。迁移只增量修改。

**验收：** 新库与已有库升级均通过；重复岗位可存储；事务失败不留下部分计划；重复迁移不破坏数据。

#### S2-02 本地后台登录会话

**依赖：** S2-01。

**开发内容：**

- 绑定成功后保存云端地址、HRPlus 用户与团队、设备和 Token 到本地会话模块。
- Windows 11 使用当前用户 DPAPI 保护凭证，优先通过已有 x/sys/windows 能力实现，不引入新加密库。
- 云端重新校验 Token 与用户归属；不通过解析客户端字段自行判断登录成功。
- 网页关闭不清除会话；网页明确退出登录时调用本地 unbind，停止新执行并清除凭证。
- 本地不可达时前端仍完成退出；本地重新连接时重新绑定当前登录用户，避免不同用户的会话与计划混用。
- 用户切换前先结束原用户持有的运行与页面动作，不能用新 Token 补传旧用户结果。
- 登录过期时将本次运行记为受阻；重新登录后可补传属于该用户的历史结果，按正常时段开始未来运行。
- 后台功能由本地服务生命周期启动和关闭，不能由网页 useEffect 是否挂载决定。

**验收：** 关闭网页后仍触发；程序重启能恢复会话；日志、接口返回与快照无明文凭证；不同 Windows 用户无法解密；过期不绕过鉴权。

#### S2-03 计划保存与权限校验

**依赖：** S2-01。

**开发内容：**

- 新增独立计划 Service 与 Store，提供内存及 PostgreSQL 实现，跟随现有后端组织方式。
- 校验团队与所有者、设备绑定、岗位访问权限、动作集合、平台真实能力、周期和时间段。

- 编辑时行锁计划并核对版本、当前运行及停止确认；不依赖前端按钮禁用作为唯一保护。

- 同一岗位允许重复，不偷偷合并同岗位条目。

**验收：** 越权、版本冲突、重叠时段与不支持动作有明确返回；重复岗位成功；执行中及停止未确认时无法保存。

#### S2-04 开始、停止、编辑的云端事务

**依赖：** S2-03。

**开发内容：**

- arm 记录用户启动意图，核对 request_id；明确停止后重启或已完成后再次开始才生成新 activation_id。
- 请求登记在计划行锁下去重，保留批次与原运行。登记 pending 或 waiting_resource 不等于取得账号执行权；同日自动间歇返回原运行。
- claim 遵循 2.7 的启动顺序，先有本地预留，再在账号级事务锁内申请统一占用，同时检查计划状态、版本、批次和设备。manual 与 plan 共用同一存储契约，不能只检查当前计划是否运行。
- 改造 ClaimPositionStart 与现有手动启动服务，使旧客户端也经过统一账号占用检查；队列中的任务不将 positions 或 TaskRun 提前写成 running。
- 成功领取时返回 owner_id 与占用凭证，暂记 starting；本地开始确认才记 running。回执丢失通过原 request_id 读取原许可，不再次领取。
- 释放接口核对 owner_id、凭证与收尾确认，旧凭证不能释放新运行。收到释放后允许下个排队请求领取；未收到确认仍保持占用。
- 完成本批次当天运行后，定时器不再创建新运行；用户明确再次开始可新建。
- stop 先持久化关闭触发并登记停止请求，再由本地执行收尾。确认停止后才写入可编辑状态。
- 停止确认带原运行和批次，迟到确认不得把新启动的运行改成停止。
- 编辑与 claim 相互排斥；一个先成功，另一个返回需要刷新或停止的结果。
- 设备暂离线时停止意图仍保存，设备同步后先处理停止，再考虑新动作；离线不是已经停止的证据。
- 新状态使用递增 sequence，重试可重复返回，旧状态不能倒退新状态。

**验收：** 计划运行中手动启动、两个计划同时启动或两个设备以同一账号启动，都只有一个账号占用者；其余记等待，不提前记 running。旧客户端也受统一检查；切换执行项复用父占用；等待时段释放后可重新领取原运行；旧释放凭证不能清除新运行。

#### S2-05 已验收单岗位模块接入多执行项

**依赖：** S1-11 已通过、S2-01、S2-04。

**开发内容：**

- 计划模块调用 M1 的小步骤与动作调度，补充可选 plan_run_id、item_run_id 和调用来源，不复制三种动作实现。
- 每条编排生成独立执行项实例，重复岗位各自保存成功数量、扫描检查点和关联 TaskRun。
- 加入主执行项游标，以及按账号、平台、岗位、动作去重的已激活消息服务表。
- 只有已经开始的执行项才能激活动作，后面未开始的回复或复打不提前启动。
- 前面已激活消息在后续项期间可穿插；同岗位重复消息项共用入口，采用最近开始项的相同动作设置。
- 穿插消息记入其真实执行项与任务记录，不记入当前主扫描项，也不改写历史统计。
- 多岗位消息按首次待处理时间、上次处理时间与执行项顺序分配，沿用 M1 的批次和公平性规则。
- 整个计划活跃期间共用浏览器执行权；自动等待时段时释放，下个时段重新申请。
- 云端以父 plan_run_id 持有账号占用，子执行项和穿插消息携带同一凭证。主项完成时结束自己的 TaskRun 和岗位展示状态；下一项与旧项消息不再调用独立账号 ClaimPositionStart 抢新占用，而是验证父凭证后取得或复用对应子记录。
- 子项切换不释放父占用；计划完成、停止、受阻或自动间歇完成收尾后才释放。自动间歇保留子项和计数，下个时段以同一父运行重新领取执行权。
- 所有执行项推进完成，再检查当前已激活消息；无当前工作则结束，不等待未来消息。

**验收：** 重复岗位、先统一找简历再回复、先回复后找简历等编排均正确；后面动作不提前执行；M1 独立单岗位回归仍通过。

#### S2-06 日期、时段、随机收尾与定时触发

**依赖：** S2-02、S2-04、S2-05。

**开发内容：**

- 使用可替换 Clock 和 RandomSource，实现本地日期、一次性、每天、每周与有效日期判断。
- 名义时段采用开始包含、结束不包含。已有运行允许延后收尾；新的手动开始不能借延后区间进入。
- 每 5 秒检查，命中工作时间后确认会话与计划状态，先原子预留本地执行权，再申请云端统一账号占用；两端许可完整后才准备页面并开始。云端占用时释放本地预留，维持等待状态。
- 手动 start 与定时触发共用一条启动路径，返回 started、waiting_time 或 waiting_device，而非一律显示已执行。
- waiting_device 对应运行 waiting_resource：检查与取得执行权使用原子操作，同时间多个请求只有一个可开始，其他请求持久登记原定时间并后延。
- 随机收尾在进入时段时生成并持久保存，重启与同日停止后重开不重新抽样。
- 到达收尾时间后只确认已领取动作；清理完成后进入下一时段等待或当日结算。
- 已经完成时不等未来复打，取消本运行活跃消息服务并释放浏览器。
- 被手动任务、其他计划或必要收尾占用时，保存一份等待请求及原定时间，不抢占当前任务。按原触发时间和稳定请求序号排队，释放时立即唤醒，默认 5 秒检查兜底。
- 后延不平移原计划时段；当前时段名义结束后不能启动新任务，等待当天后续有效时段。当天没有后续时段则记未执行或未完成报告，下个执行日从第一项开始。用户停止或停用时移除等待请求。
- 日志记录开始等待、占用任务、实际取得执行权、延迟时长和最终结果；重复轮询不反复写相同日志。
- 等待请求持久保存原触发时间、稳定队列序号、运行或启用批次、请求编号和有效时段；重试或重启不重新入队、不丢原顺序。领取成功后才更新为 running 并初始化执行数量。
- 睡眠或时间跳变后重新判定，不补跑往日、不把错过时间的复打集中当作无上限新工作。
- 相邻时段的随机延后或必要确认可能占用下一时段；执行权阻止页面重叠，并记录实际延迟。前端状态已停止不等于收尾已经释放页面。

**验收：** 人工时钟覆盖时段前、开始点、名义结束、随机结束、周末和日期到期；启动竞争不重复；上午未完下午接续。

#### S2-07 运行检查点、重启与日末结算

**依赖：** S2-01、S2-06。

**开发内容：**

- 每次候选人安全处理完成后持久化 item_run 检查点与统计，不仅保存内存变量。
- 保存主项游标、活跃消息服务、各项快照和计数、状态序号、实际时段收尾时间。
- 自动间歇仍为同一运行；设备重启后当日在时段内则继续，时段外等待。
- 用户停止先完成收尾、结算 stopped，再确认计划可编辑。再次开始创建新运行，从第一项计算新的单次数量。
- 昨天未结算运行先补结算为未完成，保留原因，然后今天按新日期从第一项开始。
- 当日提前完成后不在下午再次自动开始；用户明确开始产生新批次。
- 单项失败且页面已可靠清理，标记 failed 后推进；无法安全核对页面、存储损坏、权限失效等整体问题结束本次运行。
- 有任一 failed 或未开始/未完成项，最终报告不能显示全部成功；序列走完可结束，不必因为失败一直等待。
- 计划状态补传采用原运行 ID 和递增序号，服务端迟到响应不能覆盖本地新运行。

**验收：** 自动间歇与手动停止有不同结果；程序重启不重置原运行；跨日从第一项；失败运行不会被标为全部成功。

#### S2-08 运行关联、报告和邮件

**依赖：** S2-04、S2-07。

**开发内容：**

- 计划父运行关联每个 item_run 和原 TaskRun，重复岗位通过独立执行项编号区分。
- 按实际动作分别统计打招呼、回复、复打、索要、跳过、失败和结果待核对，不从岗位累计量反推本次数量。
- 停止、正常完成和日末未完成生成各自结束摘要；待补传状态单列，不能把“发了但待同步”算成“确定没发”。
- 报告包括计划、日期、运行、结束原因、每个执行项结果、未完成项和下次计划时间。
- 日末未完成必须有页面报告和日志；邮件使用现有 Mailer.SendCustomHTML，发给计划所有者已有通知邮箱，不能任意扩大接收人。
- 同一运行、报告类型、接收人唯一。SMTP 发送不能与数据库构成准确一次事务：一般去重重复请求；回执不明单列状态，不能承诺邮箱一定只收到一封。
- 邮件失败或未配置 SMTP 时保留页面报告和具体原因，不让计划进入停用状态。
- 本地离线无法日末上报时，重新上线后补历史报告，报告标明实际生成时间；第一版不承诺离线当天立即发出邮件。
- 后续补传成功可更新运行的同步状态，保留原报告快照与更新时间，不重新重复发送日末邮件。

**验收：** 有失败及剩余项的摘要清楚；重复上报不重复创建报告；邮件失败不影响次日运行；旧岗位任务记录仍正常显示。

#### S2-09 执行计划页面与服务层

**依赖：** S2-03、S2-04；运行联调依赖 S2-06 至 S2-08。

**开发内容：**

- 新增 `/admin/execution-plans`，在招聘管理中加入执行计划入口。
- 新增独立执行计划 API 服务和类型文件，复用 cloudRequest、localRequest 与统一错误处理。
- 列表显示计划状态、本次运行状态、下次开始时间、当前执行项，以及停止和编辑入口。
- 等待执行权时显示“等待当前任务结束”，展示原定时间及等待时长；不显示为执行失败或已经开始，进入日志后可查看实际后延原因。
- 编辑使用 AdminDialog；表单分为名称与周期、时间段、执行项三个区域。
- 重复岗位添加后生成新 item_id；第一版使用上移、下移按钮排序，先不引入拖拽库。
- 每项显示岗位名、编号、三个动作选择、优先回复及原岗位上限摘要。
- 只选回复或复打时隐藏无关找简历配置；平台不支持的动作说明原因并禁选。
- 停止按钮快速进入“正在收尾”；确认 stopped 前编辑按钮禁用。服务端拒绝时刷新状态并显示明确原因。
- 时间段外立马开始显示“等待下个执行时间”；不把 HTTP 请求成功当作浏览器已经运行。
- 能力标志缺失提示更新本地程序，不启用假的计划运行按钮。
- 执行详情按执行项显示统计和日志；结果待核对与待补传使用不同提示。
- 遵循当前会员主题变量、紧凑工作台尺寸与 MUI 组件，不改版现有整个后台。
- 实现浏览器关闭后本地执行不依赖页面；页面重新打开读取当前事实，不重发开始命令。

**验收：** 同岗位多条编排可保存；按钮状态对应真实运行；停止编辑和时间段外启动提示正确；独立页面可静态导出并被本地控制台访问。

#### S2-10 自动化测试和故障注入

**依赖：** M1 独立验收已经通过；M2 对应任务随开发建立测试，最终检查依赖 S2-09。

**时间测试：**

- 同日期重复触发、手动与定时同刻、时段边界、随机结束、周末、有效期、同日两时段、跨日。
- 不同计划同刻触发只有一个开始，其他按原定时间后延；执行权释放后唤醒且不重复入队。
- 计划与原手动接口并发、同账号跨设备并发、子项切换与旧项消息穿插，云端和本地都只认一个实际占用者；等待任务不提前写 running。
- 覆盖本地预留成功但云端拒绝、许可回执丢失、云端释放失败、迟到旧释放、旧式手动任务升级占用、自动间歇释放后重领；失败时不出现双执行者。
- 当前任务显示结束但仍在收尾时继续等待；超过原时段不能启动，自动转下个时段或当日报告。
- 全部提前完成下午不重跑；停止后重新开始从第一项；时段外开始等待。
- 时钟后移、前移、休眠恢复与离线跨日不补旧动作。

**执行项测试：**

- 同岗位不同动作项、同岗位重复打招呼项、只有消息的项、复合项。
- 前面消息动作继续，后面未开始动作不提前激活。
- 连续新消息、多个消息岗位、到期复打等待时仍有公平机会。
- 单项失败继续、整体故障结束、页面清理失败禁止切下个岗位。

**数据和补传测试：**

- SQLite 单连接事务原子性与重新打开数据库后的恢复。
- PostgreSQL 收据、次数和事件的真实事务，不以只通过内存测试代替。
- 发送前、发送后未确认、确认后事务前、事务后上报前、服务器提交后丢回执分别模拟崩溃。
- 并发重复结果、同编号不同内容、换编号重复基准、上报延迟、权限失效。
- 本地有待补传时禁止该候选人创建下一次发送意图。
- 开始与编辑、停止与旧状态、开始按钮重试等竞争。

**前端和页面测试：**

- 表单、重复项排序、版本冲突、禁止编辑、能力不支持、状态轮询和报告显示。
- 浏览器 fixture 使用标准 Locator 和真实鼠标键盘；检查未引入招聘页面脚本注入。
- 页面布局、名单顺序或当前岗位变化后仍核对身份，不操作错候选人。

**测试命令：**

- 云端后端目录执行 `go test ./internal/httpapi/...`；真实收据测试使用明确独立测试 DSN，如 `GOODHR_EXECUTION_PLAN_TEST_PG_DSN`，不连接业务数据库。
- 本地程序目录执行新增模块、localdb、positionrunner 和相关平台的定向 `go test`，再跑受影响模块全量。
- Node Worker 目录执行 `node --test test/*.test.js`，按仓库既有环境准备浏览器 fixture。
- 前端执行现有 `.test.mjs` 测试、新增计划表单与状态测试、`npx tsc --noEmit` 和 `npm run build`；按实际依赖选择最少必要工具。
- 验证 `GOODHR_STATIC_EXPORT=1` 的本地控制台构建模式，在 PowerShell 中设置环境变量后调用构建，不使用 Unix 环境赋值写法。

**验收：** 测试记录说明代码版本、通过与跳过情况、使用的测试数据库。需要真实 PostgreSQL 的测试被跳过时，不能声称已验证并发记账可靠性。

#### S2-11 Windows 真实场景验收与发布准备

**依赖：** S2-10；M1 独立验收记录必须保留并在此复查回归。

**验收脚本：**

1. 在 Windows 11 安装候选本地版本，确认原有手动任务和浏览器操作可用。
2. 创建“Java 找简历 → 销售找简历 → Java 回复 → 销售回复”，确认顺序与未激活动作边界。
3. 创建同岗位复合动作计划，模拟候选人新回复与复打到期，确认安全穿插。

5. 停止运行，等待 stopped 后修改顺序，点击开始，确认第一项执行且历史没有被清空。
6. 时段外点击开始，确认只等待，不打开招聘动作。
7. 关闭网页、本地程序重启，确认登录有效时定时安排继续。

**发布准备：**

- 使用既有 Windows 打包脚本和版本流程，不在计划中指定未核对的安装包版本号。
- 默认先在开发环境完成受控验收，发布测试环境与发布生产环境分别记录。
- 回退时先停止计划、关闭新入口，再回退程序；保留收据、运行历史和待补传结果，不删除新表来回滚。
- 观察重复运行、待补传积压、停止确认超时、消息等待时长和报告失败。阈值先用于开发验收，不夸大为生产保障。

**验收：** 数据迁移、自动化测试、受控真实页面验收与安装包检查分别提供证据；尚未完成的层次明确标注。

## 5 开发完成判定

M1 可作为独立功能交付：现有单岗位入口能够开启优先回复和运行期间定时消息检查，三动作安全切换与可靠补传通过独立验收。M1 完成不代表多岗位计划管理已经实现。

以下各项同时满足才能称为完整的执行计划功能：

- 能创建和保存真实计划，重复岗位、周期、时间段和动作设置均生效。
- 本地程序在无网页参与时可以按有效时间触发，并核对登录和权限。
- 所有招聘页面操作共用执行权，按安全边界切换，不依赖注入。
- 同日跨时段继续；手动停止后从头；次日从第一项；任务完成就结束。
- 已确认复打消息可可靠补传，云端重复请求只计一次；unknown 不盲目重发。
- 执行中编辑被前后端共同禁止，确认停止后才可修改。
- 前端状态、执行项统计、报告与实际运行一致；旧本地程序不能假装支持计划。
- 旧手动任务回归通过，增量迁移和 Windows 候选安装包完成验证。
- 真实数据库测试和受控页面验收有独立证据，未完成生产验收时不称为生产就绪。

当前阶段的交付物是本开发计划。进入实现后按任务编号推进，并持续使用原 Spec 校验产品行为。
