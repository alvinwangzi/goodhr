## 交互结果

| 操作 | 观察结果 |
| --- | --- |
| 新建计划选择执行电脑 | 列表包含当前电脑及另一绑定电脑。选择 B 后显示 B，再选回 A；保存回执为 A。没有手填任意设备编号入口 |
| 同岗位添加两项 | 第一项只回复并启用优先回复，第二项打招呼；保存后两个 position_id 相同，item_id 不同。第一次保存没有发开始请求 |
| 输入重叠时段 | 9:00–12:00 与 10:00–20:00 被拦截，警告在保存后即时核对，草稿保留；夹具写入数仍为零 |
| 删除前一时段 | 删除上午时段后，剩余输入及保存值保持 13:30–20:00，对应 810–1200 分钟 |
| 启用计划 | 列表变为已启用，编辑禁用；显示等待定时执行，没有把启用等同于正在操作页面 |
| 立马开始 | 受控 `waiting_time` 回执显示“等待下个执行时间”；只验证前端消费此回执，未以夹具证明真实时钟判断 |
| 停止请求 | 点击停止后出现具体收尾说明；确认请求后显示正在收尾，编辑仍禁用 |
| 原停止确认 | 通过夹具停止确认钩子更新事实，页面接收 SSE 后恢复已停止和编辑入口，无须人工刷新 |
| 刷新原页面 | 恢复原计划。保存、启用、停止共三次写入；立马开始请求仍只有一次，未因刷新重发 |
| 取消自动回复 | 原优先回复标记随之清除。保存回执的两个 prioritize_reply 均为 false，不遗留隐藏的无效配置 |
| 重复岗位排序 | 下移后两个原编号互换顺序，编号没有重新生成；order 为 0、1，第二次保存版本为 2 |
| 旧程序能力缺失 | 在独立重启后的夹具场景省略 execution_plans 标志，启用和立马开始禁用，已停止计划仍可打开编辑。旧场景开始计数为零 |

## 剩余验收

S2-09 的设备与表单部分已有本轮受控页面证据。完整报告、按执行项日志、下次开始及等待时长展示仍需补齐；S2-09 不能因此整体标记完成。

本地控制台静态导出和安装包访问仍未验收。现有 `local-agent-go/packaging/build_windows_installer.ps1` 注释了前端构建及打包步骤，不能把普通 Next.js 构建当作安装包包含该页面的证明。原生冷启动、旧占用处理、持久消息队列、历史设备报告、通知恢复和 Windows 全场景也仍属于原 M2 目标。

还发现开发模式的编号一致性缺口：`permissiveAgentStore.SaveBinding` 在电脑被另一账号绑定时保存替代编号，而本地 `handleSessionBind` 保存物理编号。受控页面没有覆盖这种实际多账号绑定，后续必须处理，不能以当前设备选择测试证明此场景可运行。
