# 复打招呼开发清单

更新时间：2026-09-30

## 背景

- 打招呼后部分候选人一直不回复，也不给简历。
- 用户希望隔一段时间后，对未回复的候选人主动再发一次招呼消息（复打招呼），提高转化率。
- 复打招呼作为独立任务类型 `re_greet`，与打招呼 `greeting`、自动回复 `auto_reply` 并列，可单独运行也可组合运行。
- 复打内容由 AI 根据岗位配置的复打提示词 + 聊天上下文生成。
- 第一版只做 Boss 直聘。

## 已确认决定

| 编号 | 决定 | 含义 |
| --- | --- | --- |
| R-01 | 候选人名单从云端拉取 | 支持跨客户端工作，不依赖本地历史记录 |
| R-02 | 复打间隔放个人配置 | 全局生效，所有岗位共用 |
| R-03 | 复打时间范围放个人配置 | 用户选择只复打最近 N 天内打招呼的候选人 |
| R-04 | 同一候选人最大复打次数放个人配置 | 用户自己决定最多复打几次 |
| R-05 | 复打提示词放岗位 AI 配置 | 每个岗位可以写不同的复打提示词 |
| R-06 | 拒绝检测为岗位级可选开关 | 勾选后，候选人明确拒绝再沟通的不再复打 |
| R-07 | 第一版只做 Boss 直聘 | 其他平台后续扩展 |
| R-08 | 复打消耗 AI 余额 | 需要会员权限检查，与自动回复一致 |
| R-09 | 复打名单不依赖 `source` 字段判断 | `candidate_screenings` 的 upsert 会覆盖 `source`（自动回复遇到同一人会改成 `auto_reply`），须新增独立的 `greeted_at` 字段作为"打过招呼"的判据 |
| R-10 | 复打间隔同时约束名单筛选 | 打招呼（或上次复打）后未满最小间隔的候选人不进名单，间隔不只是处理节奏 |
| R-11 | 第一版复打只发消息，不做索要简历跟进 | Boss 规则候选人回复前求简历按钮禁用；复打成功后不写入待索要名单 |

## 配置项规格

### 个人配置（全局，`user_preferences` 表新增字段）

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `re_greet_interval_min` | INTEGER | 30 | 复打最小间隔（分钟） |
| `re_greet_interval_max` | INTEGER | 50 | 复打最大间隔（分钟） |
| `re_greet_time_range` | INTEGER | 7 | 复打时间范围（天），只复打最近 N 天内打招呼的候选人 |
| `re_greet_max_count` | INTEGER | 1 | 同一候选人最多被复打的次数 |

### 岗位配置（`positions` 表 `ai_config` JSONB 新增字段）

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `re_greet_prompt` | TEXT | `""` | 复打招呼 AI 提示词，告诉 AI 如何生成复打消息 |
| `re_greet_skip_refused` | BOOLEAN | `false` | 勾选后，候选人明确拒绝再沟通的不再复打 |

## 整体流程

```
前端勾选"复打招呼" → 启动岗位运行
→ 本地 Agent 识别 task_type 包含 re_greet
→ 从云端拉取候选人名单（已打招呼 + 未收到简历 + 距上次打招呼/复打已满最小间隔 + 在时间范围内 + 未超过复打次数）
→ 进入 Boss 消息页
→ 逐个搜索候选人会话
→ 确认最后一条是我方发出（对方已回复则跳过）
→ 读取会话上下文
→ AI 判断：候选人是否明确拒绝过 + 生成复打内容（一次调用完成）
→ 被拒绝且开启跳过 → 上报跳过原因，本候选人不再复打
→ 未拒绝 → 发送复打消息 → 上报云端记录
→ 全部处理完 → 结束（只发消息，不触发索要简历）
```

### 与其他任务的串行顺序

如果用户同时选了多个任务类型，执行顺序为：

1. `greeting`（打招呼：扫描推荐列表）
2. `re_greet`（复打招呼：消息页找未回复的人）
3. `auto_reply`（自动回复：消息页回复候选人）

每个阶段完成后进入下一阶段。

    - `last_re_greeted_at`（TIMESTAMPTZ, 可空）：上次复打时间，复打成功上报时写入
    - `re_greet_count`（INTEGER, 默认 0）：该候选人已被复打的次数

#### 1.3 复打候选人查询接口

- [ ] 新增 `GET /api/positions/{id}/re-greet-candidates` 接口
  - 参数：`time_range`（天）、`interval_min`（分钟）、`max_count`（最大复打次数），均由本地 Agent 从个人配置读取后传入
  - 查询逻辑：从 `candidate_screenings` 表查同时满足以下条件的候选人：
    - `greeted_at IS NOT NULL`（打过招呼，判据不用 `source`，见 R-09）
    - `greeted_at >= now() - time_range 天`（在复打时间范围内）
    - `greeted_at <= now() - interval_min 分钟`（距打招呼已满最小间隔）
    - `resume_status != 'received'`（未收到简历，云端先过滤减少无效 AI 调用）
    - `re_greet_count < max_count`（未超过最大复打次数）
    - `last_re_greeted_at IS NULL OR last_re_greeted_at <= now() - interval_min 分钟`（距上次复打已满最小间隔）
  - 返回列表：`candidate_name`、`platform_candidate_id`、`score`、`greeted_at`、`re_greet_count`
  - 需要认证（Bearer token），并校验岗位归属当前用户

#### 1.4 复打结果上报接口

- [ ] 新增 `POST /api/positions/{id}/re-greet-results` 接口
  - 请求体：`candidate_name`、`platform_candidate_id`、`message_text`（复打内容）、`status`（sent / skipped_refused / failed）、`skip_reason`（可选）
  - 处理逻辑：
    - `sent`：更新 `candidate_screenings` 的 `re_greet_count + 1`、`last_re_greeted_at = now()`，记录候选人事件 `re_greeted_sent`
    - `skipped_refused`：记录候选人事件 `re_greet_skipped_refused`，不增计数
    - `failed`：记录候选人事件 `re_greet_failed`，不增计数
  - 需要认证

- [ ] `candidate_screening_store.go`：打招呼流程（`source='greeting'` 且 `status='passed'`）上报时在 upsert 中写入 `greeted_at = now()`，并保证冲突更新时 `greeted_at` 不被置空或覆盖

#### 2.3 复打主流程（新文件 `re_greet.go`）

- [ ] 文件作用：编排复打招呼的完整流程
- [ ] `runReGreetTask(ctx, position, options)` 主方法：
  1. 从云端拉取复打候选人名单（调用 `GET /api/positions/{id}/re-greet-candidates`，携带个人配置里的时间范围、最小间隔、最大复打次数）
  2. 进入 Boss 消息页（复用 `openChatHomePage`）
  3. 逐个处理候选人：
     a. 搜索候选人会话（复用 `locateChatSession` / `findChatSession`）
     b. 确认最后一条是我方发出的（`isUnrepliedSessionText`）
     c. 读取会话上下文（复用自动回复的消息读取能力）
     d. 如果开启拒绝检测：AI 同时判断是否被拒绝 + 生成复打内容
     e. 未开启拒绝检测：AI 直接生成复打内容
     f. 发送复打消息（复用消息发送能力）
     g. 上报结果到云端
  4. 输出本轮复打汇总日志（总数 / 成功 / 跳过-拒绝 / 跳过-已回复 / 失败）
- [ ] 复打间隔控制（两层含义，缺一不可）：
  - 名单层：云端查询已按"距上次打招呼/复打满 `interval_min`"过滤（见 1.3）
  - 节奏层：每处理完一个候选人后，随机等待 `interval_min` ~ `interval_max` 分钟再处理下一个，模拟人工节奏
- [ ] 复打统计结构 `ReGreetStats`：`Total`、`Sent`、`SkippedRefused`、`SkippedReplied`、`Failed`

#### 2.6 AI 层

- [ ] `localai/reply.go` 或新文件 `localai/regreet.go`：新增 `GenerateReGreet(ctx, request)` 方法
  - 输入：`ReGreetRequest` 包含 `ReGreetPrompt`（岗位复打提示词）、`GreetMessage`（首次打招呼语）、`ConversationHistory`（聊天上下文）、`CandidateName`、`PositionRequirement`（岗位要求）、`SkipRefusedCheck`（是否跳过拒绝检测）
  - 输出：`ReGreetDecision` 包含 `ShouldSend`（是否发送）、`Message`（复打内容）、`IsRefused`（是否被拒绝）、`RefuseReason`（拒绝原因）
  - AI 提示词构造：把岗位复打提示词 + 首次招呼语 + 聊天上下文 + 岗位要求组装成 system + user messages
  - 如果 `SkipRefusedCheck=true`：AI 不需要判断拒绝，只生成内容
  - 返回 JSON 格式：`{"should_send": true, "message": "...", "is_refused": false, "refuse_reason": ""}`
  - 拒绝检测的实际场景：复打目标是"没回复过的人"，会话里通常没有拒绝内容可检测；拒绝检测真正生效的是**第二次及以后的复打**——上次复打后候选人回过"不需要""别发了"之类的话。首次复打且对方完全没回复时，AI 直接生成复打内容，`is_refused` 恒为 false，不做额外判断

| 岗位编辑提示词 label | 复打招呼提示词（可选） |
| 拒绝检测 label | 候选人明确拒绝时不再复打 |
| 日志前缀 | 复打招呼 |
| 候选人事件类型 | `re_greeted_sent` / `re_greet_skipped_refused` / `re_greet_failed` |

## 注意事项

1. **不能注入 JS**：所有页面操作必须通过 Playwright/CloakBrowser 标准 API，复打流程复用自动回复已有的会话搜索和消息发送能力，不新增页面操作。
2. **复打间隔是随机范围**：每次复打之间随机等待 `interval_min` ~ `interval_max` 分钟，模拟人工节奏。
3. **AI 调用合并**：拒绝检测和复打内容生成共用一次 AI 调用，减少 token 消耗。
4. **会员权限**：复打消耗 AI 余额，启动前检查会员状态，与自动回复一致。
5. **幂等性**：同一个候选人不会被重复复打——云端名单按间隔下限（`greeted_at` / `last_re_greeted_at`）和次数上限（`re_greet_count < max_count`）双重过滤。
6. **先提交再开发**：开始编码前先提交已有变更。
7. **迁移编号先查目录**：migrations 目录存在 0036/0059/0068/0071 同号文件先例，新迁移文件编号必须以开发时目录实际最大编号顺延，避免撞号导致执行顺序问题。
8. **复打不索要简历**：第一版复打成功后不写入待索要名单、不点求简历（决定 R-11）。候选人若因复打而回复，由后续自动回复或岗位收尾的回复检查流程处理。
9. **greeted_at 是复打名单唯一判据**：任何依赖 `source='greeting'` 的查询都不可靠（upsert 会覆盖 source），复打名单必须用 `greeted_at IS NOT NULL` 判断。
