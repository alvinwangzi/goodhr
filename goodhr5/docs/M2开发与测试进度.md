# HRPlus M2 开发与测试进度

目标：完成执行计划详细开发计划的全部 M2 开发、自动化验证和 Windows 场景验收。当前为开发中，不能宣布 M2 完成。

## 本轮基础交付

- 新分支 codex/m2-execution-plans，从已推送且干净的 M1 基线 142509c6 开始。
- 云端配置与运行数据契约：独立执行项编号，允许同岗位重复；拒绝未知动作、重复项编号、错序、重叠时段和未选回复却优先回复。
- 增量迁移 0099：计划、窗口、执行项、运行、子运行、请求、账号占用、报告八类表。所有字段带中文 COMMENT；原 M1 收据及原岗位数据保留。计划 Store 与保存权限 API 已在第二轮接入；统一账号领取仍未完成。
- 本地 planclock：一次性、每天、每周、有效日期、明确时区与名义窗口；开始包含、结束不包含，随机收尾不作为新任务的启动许可。Windows 时区数据使用标准库内置，不下载依赖。
- 真实 SQLite 的等待请求：保留原触发时间、稳定序号、原计划与启用批次；同编号重试返回原记录，内容冲突拒绝；FIFO 在关闭重开后仍成立。该队列尚未接入运行领取与释放流程。
- 窗口收尾抽样持久化：以账号作用域、计划、日期及名义起止值保存三至六分钟延迟，重读不重新随机；错误抽样值事务回滚。

## 第二轮：保存事务与权限 API

- 新增 ExecutionPlanStore 的内存与 PostgreSQL 实现，读取按所有者和团队过滤。保存保持 stopped；重复岗位保留独立执行项，配置深拷贝防止原地修改绕过版本。
- PostgreSQL 保存先锁计划行，再核对版本、停止意图、未结算运行与尚未释放的账号占用；配置、窗口和执行项同事务提交。自动间歇、停止未确认和收尾中禁止编辑或删除。软删除不删除运行、子任务或报告。
- 注册 /api/execution-plans 与 /api/execution-plans/{id} 配置 API。使用真实登录会话决定所有者，校验实际设备绑定、当前用户岗位、开放平台和已验证动作、会员条件；不信任客户端所有者或 capability。保存不启动本地程序，尚未提供假 start/claim 接口。
- 请求限制一份 JSON、大小和字段，凭证或伪造运行状态字段会被拒绝。当前默认时区补为 Asia/Shanghai。
- 真实 PostgreSQL 验证：第二条执行项写入失败完整回滚配置/版本/原顺序；同版本两个并发编辑仅一份提交；waiting_window 以及终态后尚在 releasing 的占用均阻止编辑。删除仍保留原运行历史。
- HTTP 与内存验证：登录、设备、重复岗位、版本冲突、越权、其他用户岗位、Pro 消息权限、凭证字段拒绝，以及配置深拷贝；完整 httpapi 回归通过，明确启用独立 M2 PG 测试。
- 仍未完成 M2：受保护会话、统一执行权 claim/停止确认/严格释放、多岗位执行、后台时间触发、检查点补传、报告和前端等仍在后续清单内。未部署或启动真实招聘任务。

## 第三轮：受保护会话与账号执行权事务

- 登录保护已提交为 06989389：Windows 当前用户 DPAPI 加密保存会话，重启先向云端核对账号、团队、设备与服务地址。退出同时清除本地凭证并撤销云端旧令牌；切换账号等待旧任务完成收尾。实际本地程序两个进程的重启测试通过，第二个进程无需网页再次绑定即可恢复补传。不同 Windows 用户的实际隔离仍待验收。
- 新增迁移 0100 保存账号执行权成功请求的摘要回执，字段均有中文备注。凭证原文不落云端数据库；领取暂记 starting，本地确认开始后才记 running，释放必须核对设备、占用者、凭证和收尾确认。
- 新占用存储与既有手动 ClaimPositionStart 使用相同账号事务锁；新领取检查旧式 running 岗位，旧手动入口检查新占用。离线、心跳超时和显示终态都不会自动删除占用。
- 独立 PostgreSQL 真实事务验证：同账号十二个手动/计划及跨设备申请只有一份成功；原领取重试返回相同占用；相同编号换设备被拒绝；旧领取在释放后不能重新启动；错误凭证和未收尾不能释放；迟到旧释放重试不影响新占用。
- 本轮新增存储尚未注册为公开领取 API：权限重校验、本地预留的实际接入、计划版本与启用批次校验、运行更新同事务、手动任务完整生命周期以及内存模式仍需继续开发。当前不声称统一排队或多岗位运行已完成。

## 第四轮：计划启用与停止意图

- 接通 `/api/execution-plans/{id}/arm` 和 `/stop`。启用复用保存时的真实设备、岗位、平台及会员权限检查；按刚核对的配置版本提交，不沿用并发编辑前的权限结论。启用只返回 enabled 与独立 activation_id，不提前创建运行或操作页面。
- 内存与 PostgreSQL 保存原请求结果及内容摘要。同一请求重试返回同一批次，换内容拒绝；停止指定原批次，旧停止请求重放不覆盖后来的启用。重新启用生成新批次，未来本地从第一项创建新运行。
- 编辑、删除、启用与停止共用计划行锁。启用后需先停止再编辑；停止立即关闭未来触发，但有未结算运行或尚未释放的账号占用时保留 stop_requested，继续禁止编辑及重新启用。
- 真实 PostgreSQL 与内存契约、HTTP 路由验证通过。实际并发编辑与启用只有一个成功；终态运行仍持有 releasing 占用时，用户停止不会清掉占用或开放编辑。明确启用独立 M2 PG 的完整 httpapi 回归通过。
- 后续仍须接入设备收尾确认、统一领取与手动启动生命周期、五秒后台触发、多执行项调度、跨窗口检查点、报告及前端。云端不替本地计算即时开始时段，当前也不声称已验证多岗位实际执行。

## 第五轮：停止收尾确认

- 云端新增 `/api/execution-plans/{id}/confirm-stop`，复用原计划请求回执表；确认必须匹配真实会话、指定绑定电脑、原配置版本、原启用批次和 cleanup_confirmed。未确认、换电脑或借用旧批次不能解除保护。
- PostgreSQL 先锁账号，再锁计划行，核对关联占用已实际释放。收尾确认和父运行、子项结算及解除 stop_requested 同一事务保存；跨窗口 waiting_window 记录可结算，原动作计数保留。结束时间和状态序号同步写入。
- 成功确认重试返回原结果，不重复推进序号；原确认迟到不影响重新启用的新批次。内存模式对终态但仍持有占用的运行补齐同样保护。
- 真实 PG 验证实际领取后未释放仍拒绝确认，按原凭证安全释放后才能结算并编辑；内存及 HTTP 验证缺少收尾确认、其他电脑、重复回执与迟到旧批次。
- 本地调用方仍待接入，不能把云端确认 API 已通过测试等同于实际页面收尾已验收。统一启动、计划调度、报告、前端及完整 Windows 场景仍未完成。
