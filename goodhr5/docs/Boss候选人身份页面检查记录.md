# HRPlus Boss 候选人身份页面检查记录

检查日期：2026-10-08。

用户在 Codex 内置浏览器完成招聘者登录后，检查了推荐卡片、聊天列表、姓名搜索和在线简历入口。全程只使用标准 Locator、鼠标点击、页面刷新和截图；没有脚本注入，没有发送消息、打招呼或索要简历。打开已有会话可能影响网站自身的已读状态。

本记录省略候选人姓名、公司、完整履历和完整身份值。它是页面观察证据，不表示 HRPlus 代码已经实现或通过功能验收。

## 1 实际观察

| 入口 | 标准读取方式 | 结果 |
| --- | --- | --- |
| 推荐列表 | recommendFrame 内 `.card-inner` 的 `data-geekid` 属性 | 多个候选人卡片存在不同的长字符串标识，外围 `.candidate-card-wrap` 不提供该属性 |
| 聊天列表 | `.user-list .geek-item` 的 `data-id` 属性 | 存在不同的会话标识，本次观察格式为数字加后缀 |
| 当前选中会话 | `.user-list .geek-item.selected` 的 `data-id` | 点击不同会话后可读到对应标识；需要等待异步选中状态更新 |
| 姓名搜索结果 | `.geek-search-list ul li` 的常用身份属性 | 样本中没有 data-id、data-geekid 或 data-uid，不能直接从搜索条目读出会话标识 |
| 搜索后的聊天入口 | 打开搜索结果，再读取 selected 会话项 | 样本中会对应到聊天列表的相同 data-id，不需要把姓名当唯一身份 |
| 展开的聊天面板 | `.chat-conversation` 的常用身份属性 | 样本中没有 data-id 或 data-geekid，只有姓名和岗位核对不足以确认同名者 |
| 聊天在线简历 | c-resume iframe 的 src、页面常用身份属性与链接 | src 仅包含 chat-resume-online 来源；样本未读到可关联候选人的身份属性或 href |
| 推荐候选人详情 | recommend 来源的嵌套 c-resume iframe | src 不带卡片标识，样本未读到可与聊天 ID 直接关联的身份属性 |

只检查了上述属性和入口，不据此宣称页面所有元素都没有其他身份字段。未读取页面内部运行状态、网络响应或隐藏脚本状态。

## 2 同名样本

真实列表中发现两条姓名相同的会话；搜索结果的姓名和公司文本也相同。

- 会话 A 的标识为 `774***333-0`。
- 会话 B 的标识为 `747***083-0`。
- 分别打开两个搜索结果后，选中列表项分别对应 A 和 B。
- 刷新页面后，两条列表记录的完整原值均与刷新前一致。

这说明本次账号与页面中，同名搜索入口可以通过打开后的选中会话标识区分，不能以姓名或公司作为唯一身份。

## 3 搜索目标不在当前列表的情况

切换到未读列表后，上述样本不在当前列表中。通过姓名搜索打开后，页面将相应候选人加入并选中到聊天列表。

点击刚完成时，立即查询 selected 返回零项；页面更新后返回唯一 selected 项及正确标识。因此实现必须等待“目标选中状态已经更新”，不能点击后立即取旧状态或把暂时没有选中项当作身份不存在。

同名场景还需防止沿用前一个人的 selected 项。后续实现应使用每次选择前后的会话状态、目标标识和页面准备完成条件核对；首次没有可靠目标标识时不能仅凭同名面板就自动发送。

## 4 可据此采用的实现方向

1. 推荐候选人扫描应保存页面实际提供的 data-geekid，并保留其来源与账号作用域；不能继续把姓名加年龄生成的值标成 Boss 的真实候选人 ID。
2. 自动回复以聊天列表 data-id 定位会话；发送前核对唯一 selected 会话标识与当前目标一致，岗位和姓名作为额外检查。
3. 已经保存 conversation_id 的复打目标优先按 ID 定位。同名搜索只用于打开或重新发现会话，打开后必须与目标 ID 对照，不以搜索结果顺序作为发送身份。
4. 搜索入口没有直接标识时，可通过逐个查看结果获取会话 ID，但只有与既有目标 ID 匹配后才允许发送；没有目标映射时保留待核对。
5. 保留完整会话标识及后缀。当前未验证后缀含义，不能擅自去掉后缀或假定它与某个岗位编号有关。
6. 同名、同名同公司、选中状态迟到、搜索目标原本不在列表及页面刷新场景，应加入单岗位 M1 身份验收。

## 5 仍待确认的对应关系

推荐卡片的 data-geekid 是长字符串；聊天列表 data-id 是另一种格式。本次没有证据证明二者相同、能直接转换，或已经存在可靠的对应关系。

下一步需要在获得候选人到会话的直接跳转证据时，建立来源候选人标识与 conversation_id 的映射。例如在已授权的首次打招呼流程中，由确定的候选人入口进入其会话再记录对应关系；不能单凭同名搜索推断。此次检查没有为验证映射额外发送新消息。

历史姓名年龄记录无法唯一关联时，不自动合并、不猜测转换到新标识。标识在本次刷新后稳定，但跨日、退出重登、不同账号或不同岗位入口的稳定范围尚未验证。

该对应关系验证属于 M1 单岗位身份处理，不依赖 M2 多岗位计划管理。

## 6 推荐列表切换和刷新检查

同日继续按用户要求检查“推荐牛人 → 沟通 → 推荐牛人”和整页刷新。未处理真实招聘业务，仅记录页面身份与顺序进行对照。

| 操作 | 本次样本 | 观察结果 |
| --- | --- | --- |
| 菜单来回切换 | 切换前记录 29 个卡片，回来后页面已加载 89 个卡片 | 原 29 个候选人均再次出现，其完整 data-geekid 无变化，原样本顺序保持一致 |
| 整页刷新 | 刷新前已加载 89 个卡片，刷新后的首批读取 14 个卡片 | 14 个再次出现的候选人完整 ID 都与原值相同，14 人在列表中的位置均发生变化 |
| 位置示例 | 原列表第 60 位、34 位、30 位的三个候选人 | 刷新后分别位于第 1 位、2 位、3 位 |
| 最后处理位置的模拟 | 假定原列表第 3 位为最后处理的人 | 此 ID 不在刷新后读取的首批 14 人中，不能要求恢复时必须先找到他 |

这里的数量是当次已经加载并读取的 DOM 卡片数量，不是招聘平台全部候选人总数。刷新后的新候选人顺序与推荐结果可变化，未验证某个 ID 永久不变或跨账号通用。

结论：本次样本支持以完整 data-geekid 判断同一推荐候选人，菜单切换和刷新后的恢复不能依赖旧序号。

## 7 扫描恢复方案建议

用户后续确认采用“最近三个已处理候选人 ID 与顺序”的快速检查。以下方案据此更新，三锚点是恢复位置优化，不能据其宣称整个页面没有刷新。

- 保存当前单次运行的已完成候选人 ID 集合、明确处理结果、尚未处理队列、最后处理 ID 与成功打招呼数量。
- 切换前另存最近三个已处理者的完整有序 ID；不足三人保存已有者。返回时先核对岗位、筛选条件与对应位置的锚点，全部匹配时从该位置快速继续。
- “已读到卡片”不算处理完成；成功确认、明确跳过或明确结束判断后才登记本次完成。处理中、待重试和结果待核对分别保存。
- 三锚点匹配时不从头遍历历史列表，对继续处理的候选人按 ID 查询本次结果；锚点不匹配、缺失或无法确认时，从当前列表起点重新检查：未完成则处理，已完成则跳过。
- 局部三个 ID 保持不变时，未处理者仍可能移动到锚点前。用户选择的快速路径不保证发现这一部分变化，验收限于恢复位置和后续处理不重发；不要求每次返回或完成前追加一次全列表核查。
- 最后处理 ID 只是恢复位置的参考。如果列表重新排列，不能直接跳过它前面的全部候选人，否则会漏掉新出现或移动到前面的未处理者。
- 最后处理的人暂时不在当前批次时，从当前列表按 ID 检查并继续，以真实滚轮读取后续候选人，不无限寻找旧位置。
- 只有已保存的顺序邻接信息与当前列表一致，且跨过的候选人都确认完成时，才可以用最后位置加速定位。
- 本次完成集合关联运行与岗位；后续多岗位模式再关联执行项。跨日期或新执行项是否重新筛选按任务规则处理，不能把“本次处理过”解释为永久跳过。
- 已打招呼、回复去重及复打次数等联系历史继续使用独立约束；结果不明时不能因恢复扫描而再次发送。

该方案仍是实现建议，本次没有修改业务代码或把查看过的候选人写成已处理。
